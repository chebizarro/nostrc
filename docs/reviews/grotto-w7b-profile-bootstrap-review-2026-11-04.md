## Severity-ranked findings

### F1 — P1 / High / Confirmed: discovery bootstrap can request signing and send identity AUTH

**Evidence:** `apps/grotto/src/grotto-profile-service.c:209-231,295-307,405-409,426-429,629-642`; downstream `apps/grotto/src/grotto-profile-service.c:94-115` and `apps/grotto/daemon/grotto_control.c:858-885`.

Preconditions: no cached signed NIP-65 list or usable configured relay; bootstrap enabled; a contacted bootstrap relay sends a nonempty `AUTH` challenge before that fetch is done. `discover()` sets `bootstrap_round`, but `fetch_relays()` gives every connection the real identity signer and the ordinary `fetch_frame()` listener. That listener checks neither `bootstrap_round` nor a discovery-only capability before building kind 22242 with the target identity's pubkey, requesting its signature, and sending `["AUTH", signed_event]`.

The actual signature goes through `SignProfileEvent` and its existing one-time review. This is **not evidence of silent signing, secret-key disclosure, or an approval bypass**. Nevertheless discovery itself initiates signing, and approving that prompt supplies ownership proof to a bootstrap relay. The user's requirement expressly disallows both the signing attempt and the AUTH response, even with a separate prompt. [NIP-42](https://github.com/nostr-protocol/nips/blob/master/42.md) distinguishes this signed authentication from a public author-filter query.

**Required containment:** bootstrap fetches must have no usable signing capability and must reject/skip AUTH-required access without responding; keep normal identity-outbox AUTH behavior separate. The existing bootstrap test rejects `EVENT` publication, not AUTH (`apps/grotto/tests/test-profile-integration.c:149-160,234-236`). Add a challenge-emitting bootstrap fixture and assert zero signing requests and zero outgoing AUTH, for both Fetch and Save-triggered discovery.

### F2 — P2 / Medium / Confirmed: the signing review does not disclose bootstrap discovery provenance

**Evidence:** `apps/grotto/src/grotto-profile-service.c:104-115,414-431,520-541,678-683`; `apps/grotto/daemon/grotto_control.c:879-885`; `apps/grotto/src/ui/approval_dialog.c:894-902,918-931`; editor `gnome/grotto-panels/src/grotto-profile-view.c:96-98,314-321`.

The profile page/editor can disclose discovery URLs behind a disclosure row. However the actual signing RPC carries only identity, unsigned event and **publication destinations**. The daemon's review reason lists publication relays (or the AUTH destination), and the approval dialog has no bootstrap-used flag or contacted-discovery list. Thus an actual signing review following bootstrap discovery does not contain the required bootstrap disclosure. Editor details are not disclosure in that separate review.

This is particularly visible when Save discovers a previously absent 10002: `discover()` accumulates the contacted bootstrap URLs, then calls the signer; those new results reach the panel only after completion. The editor's details remain bound to the preceding `self->info`. A bootstrap AUTH review from F1 also lacks discovery-only context. The exact JSON and final publish destinations themselves remain present; this finding is about the additional required provenance, not missing publication scope.

**Required correction:** carry non-authorizing discovery provenance into the same trusted review, clearly separated from publish destinations, including contacts first made during Save. Test the rendered review, not just the returned info struct or presence of the editor disclosure.

### F3 — P2 / Medium / Confirmed: the final upload signing review still says the original image is uploaded

**Evidence:** new crop/confirmation path `apps/grotto/src/grotto-profile-service.c:693-702,734-758,774-789`; upload `apps/grotto/src/grotto-profile-service.c:566-581`; unchanged downstream impact text `apps/grotto/src/ui/approval_dialog.c:900-902`.

The local crop dialog accurately promises a re-encoded PNG with original embedded metadata removed. Crop output replaces `j->bytes` and `j->mime`; upload hashes/signs/uploads those new bytes. But the later, actual authorization review says Grotto uploads the **original image**. An ordinary cropped upload therefore has contradictory consent text at the final signing boundary. This is stale wording newly made false by W7b, not evidence that the original/EXIF bytes are actually uploaded.

**Required correction:** make the authorization impact describe the reviewed cropped/re-encoded image. Keep the independent immediate-publication and cancellation warning. The current authorization-preview test checks tags/hash/scope and absence of generic “does not publish” wording, but not this claim (`apps/grotto/tests/test-profile-integration.c:374-397`).

### F4 — P3 / Low / Plausible UX ambiguity: Republish submits unsaved edits, not the last published content

**Evidence:** `gnome/grotto-panels/src/grotto-profile-view.c:122-135,181-193,203,327-329`; production reconstruction `apps/grotto/src/grotto-profile-service.c:523-541`; test `gnome/grotto-panels/tests/test-profile-panel.c:119-122`.

Republish is wired to the exact same callback as Save. If an already-published profile has unsaved edits, Republish publishes the current draft in a new event. A user could reasonably interpret the separately offered Republish action as retrying the existing profile without those edits. The final exact-JSON review mitigates this, and the spec does not explicitly define draft behavior, so this is **not a confirmed custody violation**. Clarify the label/subtitle or disable the distinction while dirty. The existing test clicks Republish only after reopening an unchanged form and does not settle this ambiguity.

## 1. Bootstrap containment: checked boundaries

- **Only three discovery kinds:** `kinds` includes 0/10002/10063/10050, but `send_req()` excludes 10063 in `bootstrap_round`, creating three author-pinned, `limit:1` filters (`apps/grotto/src/grotto-profile-service.c:19-20,179-186`). The incoming event handler independently excludes 10063 in that round (`:261-273`). This is not a general relay subscription or media-server bootstrap.
- **Only when relays are unknown:** verified cached 10002 wins; otherwise configured read/write relays are tried. Bootstrap is selected only if that list is empty, there is no identity relay configuration file, and the enable setting is true (`:362-377,397-410`). Explicit empty identity configuration suppresses bootstrap. The generic relay schema default is not silently used here: `configured()` reads only a user value (`:368-374`).
- **Opt-out:** Fetch and Save share this selector (`:641-642`); Preferences binds the enable switch to GSettings and allows list editing/removal/reset (`apps/grotto/src/ui/page-settings.c:131-181`). Disabling discovery prevents subsequent bootstrap selection; it does not erase cached metadata or prohibit querying already-known identity relays. An already-started batch snapshots settings; immediate revocation of in-flight traffic is not implemented or tested, and is not asserted here.
- **Defaults in one production data location:** `apps/grotto/data/org.nostr.Grotto.gschema.xml:105-114`; the service reads that key and Restore Defaults uses `g_settings_reset`, not a second compiled list (`apps/grotto/src/ui/page-settings.c:152-158`). The Preferences description discloses that discovery exposes the public identity (`:160-170`). Successful fetch provenance is visible in profile/editor details (`gnome/grotto-panels/src/grotto-profile-view.c:96-98,314-321,396-401`). The separate review gap is F2.
- **Signed-cache verified handoff:** `verified()` deserializes a signed event, validates it, and checks both kind and the selected identity's exact hex pubkey (`apps/grotto/src/grotto-profile-service.c:52-59`). Both cache reads and received candidates use it (`:65-69,261-273`). Only those admitted events populate `events[1]`, which is parsed for NIP-65 WRITE/outbox URLs before the second round (`:401,426-429`). Cache writes repeat verification and monotonic timestamp/ID selection (`:71-91`). No reliance on a bare unsigned cached relay array was found.
- **No bootstrap publish fallback:** `save_profile()` uses verified 10002 WRITE relays or configured write relays, never `profile-bootstrap-relays`, and fails without destinations (`:520-522`). Kind 10050 is cached, not used as a profile-publish or outbox destination. A bootstrap URL independently listed by the identity's signed outbox/config is a different authority source; this review does not require a hostname blacklist for that case.
- **Protocol boundary:** EOSE is successful catch-up; CLOSED/disconnect/deadline are not empty-profile success (`:188-195,254-280,433-435`). NIP-11 probes run independently and contain no identity parameter (`:134-148,284-305`). Publishing observes matching OK verdicts, including failure (`:244-252,514-563`). These good patterns do not cure F1: discovery still has AUTH signing authority.

## 2. NIP-05 verification

**No confirmed defect in the requested HTTPS/redirect/authority/privacy properties.** `verify_nip05()` validates the restricted local part and ASCII domain characters, builds only `https://<domain>/.well-known/nostr.json?name=<name>`, uses a 10-second Soup timeout, disables redirects and caps the response at 64 KiB (`apps/grotto/src/grotto-profile-service.c:586-611`). The pubkey is compared locally; it is not appended to the URL or sent to a third-party verification service. Returned relay hints are not consumed. This follows the direct-domain mapping in [NIP-05](https://github.com/nostr-protocol/nips/blob/master/05.md).

The result is textual match/mismatch/invalid/unavailable/unchecked status, not identity/signing authority (`gnome/grotto-panels/src/grotto-profile-view.c:52-60,71-76,99-100`). Changing the address resets its status; Check revalidates it (`:133-141,208,287-290`). Automatic checking occurs after online metadata discovery; otherwise checking is explicit (`apps/grotto/src/grotto-profile-service.c:650-652,678-683`). The domain learns the requested identifier and network connection; no claim of anonymity is made. Tor mode blocks the network path (`:633-640,652`). No live DNS/TLS/redirect/timeout execution was done here. ASCII/punycode-only address support is a limitation, not an authority grant.

## 3. Images

- **Local before upload:** the native-file requirement, bounded file read and raster decode precede the crop dialog (`apps/grotto/src/grotto-profile-service.c:710-720,791-802`). Crop/zoom/position work on local decoded pixels; a new PNG is created, previewed and frozen before the worker can upload (`:722-758,774-789`). Original file metadata is not copied into the output buffer. F3 concerns review wording, not an observed byte leak.
- **Limits:** PNG/JPEG/WebP are selected by signature before decoding; SVG is not sent through a generic loader. Input limit is 5 MiB, 8192 per side and 24 megapixels (`:17-18,454-486`). Crop output is square up to 512×512 or 3:1 up to 1500×500 (`:734-745`), with visible guidance (`:780-784`).
- **Retracted 2026-11-05 by owner decision:** the image-consent requirement below is historical. Profile Fetch now auto-loads avatars and banners for own and watch-only identities, controlled by the default-on “Load Profile Images” preference and the existing Tor cutoff. Image downloads follow at most five validated HTTPS redirects; failures leave placeholders without an error.
- **Origin consent preserved (historical):** ordinary Fetch loads only cached image bytes, not remote origins (`:644-649,488-512`). Explicit Load Images presents avatar/banner URLs, own/watch-only scope and network-address exposure with Cancel default; only affirmative Load reaches online download (`:704-708,722-731,820-822,653-662`). Downloads disable redirects and reuse size/raster limits (`:495-500`). Cached textures may reappear without new network access; this is not a fresh origin contact.
- **Preview stays non-networking:** card rendering uses supplied `GdkTexture` objects only (`gnome/grotto-panels/src/grotto-profile-view.c:62-76`). Editing an image URL clears its old texture (`:122-126,137-141`). Load in the card goes through the same host consent route (`:196,261-262`); uploaded local crops can be previewed without fetching the returned URL. No auto-loading URL widget or network-aware rich-text/link renderer was found.
- Upload is independently public before Save; cancelling/discarding does not retract it. Both the crop confirmation and Discard text say so (`apps/grotto/src/grotto-profile-service.c:695`; `gnome/grotto-panels/src/grotto-profile-view.c:209-220`).

## 4. Consent and editor action semantics

Save constructs one final kind-0 event, preserves unknown JSON fields, includes bot, pins the identity and passes the explicit publication relay set into one signing call (`apps/grotto/src/grotto-profile-service.c:520-541`). The daemon carries that exact event into the existing management gate with destinations; the review displays all fields, exact profile JSON, exact unsigned event JSON and publication impact (`apps/grotto/daemon/grotto_control.c:831-845,867-885`; `apps/grotto/src/ui/approval_dialog.c:536-546,894-902,922-931`). The returned signature is checked against the computed event ID and selected identity (`apps/grotto/src/grotto-profile-service.c:123-130`). After publication, refetch does not sign another kind-0 event (`:663-674`). **The one kind-0 review is preserved; F2 is the missing bootstrap context within that review.**

Outbox AUTH and image-upload authorization can require their own distinct one-time reviews; “one review” must not be advertised as one total dialog for every network/image action. Bootstrap AUTH is separately prohibited by the present scope (F1). Discard restores the fetched baseline locally and makes no publish/delete request (`gnome/grotto-panels/src/grotto-profile-view.c:209-220`). Save failures leave the form open; partial ACK and cancellation warnings do not pretend that sent data can be recalled (`apps/grotto/src/grotto-profile-service.c:555-561`; `gnome/grotto-panels/src/grotto-profile-view.c:170-199`). Republish remains review-gated; its draft ambiguity is F4.

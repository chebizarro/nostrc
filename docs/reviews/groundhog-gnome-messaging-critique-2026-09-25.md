# Groundhog GNOME messaging plan: bounded critique

**Status:** folded-into-plan — all 8 findings already incorporated into `docs/plans/groundhog-gnome-messaging-2026-09-25.md`; see `docs/investigations/gnome-gtk-nostr-planned-not-implemented-2026-09-26.md` (Cluster 1).

## Context / scope

Reviewed `docs/plans/groundhog-gnome-messaging-2026-09-25.md` against **only** the export's Generated Plan/Response (`prompt-exports/oracle-plan-2026-09-25-205031-groundhog-messaging-ae4b.md:165-499`). The export's prompt and selected-file list are context, not a preservation baseline. This is a plan critique, not implementation or acceptance evidence. Source checks are limited to the seams below; findings are ordered by impact.

The plan correctly replaces, rather than loses, the export's new NIP-46 client, legacy kind-443 KeyPackages, one-recipient/no-self-copy DM, kind-10002 DM fallback, GObject-client admin/save assumption, unencrypted MLS database, default sender preview, and global `nostr:` handler (`plan:20-25,40-49,58-77,120-124`; `export:197-212,294-309,383-395,437-449`). Do **not** restore those export choices. Current [NIP-17](https://github.com/nostr-protocol/nips/blob/master/17.md) and [adopted Marmot transport](https://github.com/marmot-protocol/marmot/blob/master/transports/nostr.md) support the protocol corrections.

## Findings

### High

1. **MLS deduplication names the wrong identity.** The plan's shared admission rule says to dedup by event ID plus account/backend scope (`plan:52,83`); neither plan nor export distinguishes Marmot's post-decryption replay key. The [adopted transport's duplicate/replay rule](https://github.com/marmot-protocol/marmot/blob/master/transports/nostr.md) says kind-445 Nostr IDs are transport evidence, **not** the Marmot dedup ID; dedup is over recovered MLS message bytes before state application. Keep an outer-ID cache for cheap relay redelivery, but make the authenticated MLS message ID the state-changing dedup key. Test two distinct signed 445 envelopes carrying the same MLS bytes, including across relays/restart; otherwise a second envelope can apply a Commit twice.

2. **One pool does not by itself preserve protocol relay boundaries.** Both designs choose one shared pool (`plan:52`; `export:338-348`), and the plan correctly asks for URL provenance and separate handles. The existing `gnostr_pool_query_urls_async` already solves *targeted one-shot queries* (`nostr-gobject/include/nostr-gobject-1.0/nostr_pool.h:153-174`), so do not invent another query API. Live subscriptions are different: `gnostr_pool_subscribe` uses the *first connected* relay (`:230-249`), while `gnostr_pool_subscribe_multi` uses *all connected* relays, including later connections (`:251-313`). Separate handles and post-receive provenance cannot target NIP-29 live REQs only to the authoritative relay, DM inbox REQs only to the account's 10050 relays, or MLS routing REQs only to routing-state relays. Specify a per-subscription relay-target API/connection partition (or named separate pools) and test REQ destinations plus late relay additions; keep the shared-pool optimization only if that contract is proven.

3. **NIP-29 pending join is not an accepted `OK` awaiting a snapshot.** The plan says “9021 accepted as a request” and asks for distinct pending/rejected UI (`plan:67,150`). [Current NIP-29's join rule](https://github.com/nostr-protocol/nips/blob/master/29.md) instead requires the relay to **reject** 9021 when the user has not yet been added; its rejection reason may mean pending review, final rejection, payment, or `duplicate:`. Define parsing/ownership of the rejecting `OK` reason and subsequent authoritative 9000/39002 observation before enabling post/member UI. Test pending-rejection→later admission separately from final rejection and duplicate. The export's generic “publish success→refresh” moderation pattern (`export:308-312,375-381`) is not sufficient for join.

4. **MLS message save and group-state staging are still conflated.** The export's send sequence invokes `marmot_save_created_message` and then publishes (`export:383-391`); the plan improves this to signed-event persistence, outbox and staged commit/rollback (`plan:72-75`) but leaves the concrete transaction boundary unspecified. `libmarmot/src/messages.c:477-540` shows `marmot_save_created_message` saves a message and group recency; it is not an API for staging an MLS group-state Commit. The [adopted group-state lifecycle](https://github.com/marmot-protocol/marmot/blob/master/protocol-core/group-state.md) separates `Stable`, `PendingPublish`, `Merging`, `Recovering`, and `Unrecoverable`. W2 must name the durable state owner and atomic record for staged MLS state, signed event, target snapshot and per-target attempts; define restart classification after each write/OK/apply boundary. Keep app-message persistence separate from commit staging and gate W6 on crash/restart tests of both.

5. **Background notification availability conflicts with the launch gate.** The goal and Done-when require alerts with the window closed in an active GNOME session (`plan:5-13`), but the lifecycle section allows shipping without a background service if foreground-only behavior is disclosed (`plan:54`), and W7 defers the service until after all three messaging paths (`plan:138-143`). Disclosure does not meet that launch criterion. Choose the user-service/DBus activation owner in W0/W3, establish one instance and account-generation contract before protocol services register callbacks, and make closed-window delivery an actual release gate. The export has no background process contract at all (`export:338-362`); this is a gap in both, not a reason to weaken the plan.

### Medium

6. **The export's signer operation matrix was generalized to availability states.** The generated response explicitly specifies cancellable NIP-44 encrypt/decrypt methods on the signer service (`export:279-294`) and manual local-only, NIP-55-only, NIP-46-only and none tests (`export:483-490`). The plan has better identity verification and cancellation rules (`plan:40-42`), but W3 checks method *states* and later verification checks selected failures rather than successful NIP-44/sign-event operations for every supported method (`plan:133-159`). Preserve the operation-level matrix: selected-pubkey binding, sign, encrypt, decrypt, cancel during account switch, and a full DM send/receive path per available signer. NIP-55L unavailability on a host is an explicit skip, not a simulated pass. This is the main supported implementation-bearing detail weakened from the export.

7. **The DM conversation key wording can split one room by speaker.** `plan:59` says the key is “the author's pubkey plus the set of `p` recipients.” [NIP-17's chat-room rule](https://github.com/nostr-protocol/nips/blob/master/17.md) defines the participant set from each rumor's `pubkey` **and** `p` tags; if `(author, p-set)` is stored literally, replies from the other author produce different keys. Specify a canonical participant-set key independent of who sent the individual rumor, while retaining the sender as message metadata. Test A→B, B→A and self-copy collapsing into one room, and a third participant creating a new room. The export's `peer -> conversation` map (`export:300-304`) only covers the two-party approximation; the plan's multi-recipient scope needs the canonical form.

8. **The merged-list update contract was lost.** The export specifies backend change signals, main-thread `GhConversationStore` updates, `items-changed`, and the sidebar binding only to that list (`export:316-326`). The plan preserves a typed merged `GListModel` but not who serializes backend updates, emits list mutations, or retains stable row identity under reorder/account switch (`plan:33-35,110-111`). Keep that small interface contract, with tests for simultaneous EOSE/live updates, unread reorder and late callbacks after account switch. This is not a request to restore the export's protocol-erasing `GhGroupService`.

## Recommendations / design-order questions

1. Before W1/W3, decide whether the installed pool API will gain per-subscription relay targeting or Groundhog will use isolated pools. This determines query/REQ ownership and the tests for all three backends.
2. Before W2, decide the exact durable MLS staging/outbox transaction and encrypted-state key/restore policy, plus the legacy-443 coexistence mode. Do not let `save_created_message` stand in for a group-state staging API.
3. In W0, choose the target GNOME session-service activation/stop policy and the independently reproducible adopted-Marmot interop peer. Both materially change W2/W3/W7 order and release evidence.
4. Retain the plan's specific protocol, storage, admin, privacy and version gates; amend only the contracts and tests above. No product-scope expansion or plan rewrite is needed.

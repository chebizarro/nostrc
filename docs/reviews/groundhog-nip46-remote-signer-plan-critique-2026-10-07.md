# Groundhog NIP-46 remote-signer plan: focused critique

## Context / scope

Reviewed `docs/plans/groundhog-nip46-remote-signer-2026-10-07.md` against **only the generated response** after `## Generated Plan` in `prompt-exports/oracle-plan-2026-10-07-154715-groundhog-nip-46-pla-f412.md`, then checked the named code seams. The plan's §4.1 switch to Groundhog's relay stack is intentional and sound for Tor; this review does **not** ask to restore the export's libnostr client-session/proxy design. No implementation was changed.

## Findings

### 1. Implementation-bearing export content lost or weakened

- **Real relay verification disappeared.** The export's implementation order (§6 steps 2–3) requires a local kind-24133 relay/signing fixture and a loopback SOCKS destination test. Plan WI-1/WI-5 emphasize the injected fake bunker and a transport/net-session assertion (`plan:210–219`), which can pass without proving actual REQ/EOSE, signed EVENT/OK, disconnect, or fail-closed Tor dialing. Retain one wire-level local-relay acceptance test in addition to the fast fake-transport tests; adapt it to the Groundhog stack, not the library session.
- **Durability cases narrowed.** The export explicitly tests interrupted credential store/delete and noninteractive locked-keyring lookup (generated §6 step 4), plus NIP-04 restart with zero signer RPCs (step 8). Plan WI-2 lists round trip/locked/conflict but not interrupted writes or no-prompt lookup (`plan:212`); WI-6's zero-RPC restart case covers only NIP-17 (`plan:216`). These are acceptance criteria for the promised credential/cache lifecycle, not optional extra features.
- **Artifact boundary is less explicit.** The export says AppImage remains unshipped and distribution-specific debs must be validated (generated §4, §6 step 10). The plan's WI-8 and release cut (`plan:218,237–239`) instead predict an alpha-3-like 17-file set. State which recipes/artifacts are actual alpha-4 gates and do not count AppImage or unfinished targets as shipped; this does not require adding an artifact.

### 2. Under-specified or contradictory seams

- **Codec/build seam is not implementable as written.** `nostr_nip46_build_encrypted_request_event()` takes an opaque `NostrNip46Session *`, not a raw client secret (`nips/nip46/include/nostr/nip46/nip46_envelope.h:25–33`); its implementation calls session-owned transport crypto (`src/core/nip46_envelope.c:55–69`). Thus `plan:149,180` cannot both use that builder in `GhNip46Session` and leave `nips/nip46` unchanged. Decide before WI-1 between a stateless NIP-44/envelope API in `nips/nip46` or using its plain envelope builder with explicit NIP-44 encrypt/decrypt and event signing in Groundhog; test both QR and established-session paths. The envelope builders return **unsigned** events (`nip46_envelope.c:16–32`), while `GhRelayPublish` rejects an unsigned/bad-signature event (`gh-relay-publish.h:144–156`). Also, `nostr_nip46_core` currently packages session, URI, envelope and message sources together (`nips/nip46/CMakeLists.txt:6–19`): specify the codec-only target/link split if that separation matters, rather than promising it in Groundhog CMake alone.
- **Pairing does not need a selected account or account AUTH, but its AUTH policy is unstated.** Scope/publish constructors accept a caller-supplied generation and do not require an account signer (`gh-relay-scope.c:155–175`; `gh-relay-publish.c:147–177`); each URL defaults to AUTH `NONE` (`gh-relay-scope.h:11–24`; `gh-relay-publish.h:28–45`). Allocate a pairing-attempt generation and use `NONE` for ordinary relays. Specify what happens on NIP-42 `auth-required`/CLOSED/OK, and whether an ephemeral AUTH identity is supported on protected signer relays; never silently fall back to account AUTH or a direct transport.
- **Request-vs-publish completion is undefined.** Each `GhRelayPublish` sends one event on private per-relay connections, does not retry it, and reports only relay-local OK (`gh-relay-publish.h:11–27`); its relay deadline is clamped to 300 s (`:163–171`), shorter than the proposed 330/600 s RPC windows (`plan:151`). Define when a request starts its approval timer, what happens when all relay publishes fail or some accept but none answer, how a new publish waits for the scope's first EOSE/reconnect, and which operation owns/cancels each publish. A persistent subscription is not a persistent publish channel.
- **The later key-binding check has no corresponding handshake.** `plan:191` promises `get_public_key` mismatch detection on later connect, but §5.5 describes startup subscription/ping and RPCs, not a later `connect`/`get_public_key`. Specify a resume probe before declaring `READY` (and how denial/offline differs from key mismatch), or drop the unsupported later-connect assertion while retaining signed-event author validation.
- **Selection migration is not automatically atomic.** `g_settings_delay/apply` (`plan:98`) may notify separately for `current-backend` and `current-npub`; the current controller reacts to individual setting changes (`gh-account-controller.c:247–259`). Specify pair-level reconciliation/signal suppression so the promised single generation bump and no transient wrong-backend binding are actually guaranteed. Also define read-only selection's backend value and migration ordering relative to the controller's constructor-triggered discovery (`gh-account-controller.c:261–289`).
- **Storage gate needs an earlier and stronger edge.** `gh_account_store_continue_without_saving()` really exists (`gh-account-store.c:769–784`) and is invoked by `gh-app-services.c:509`; disabling only the method leaves the app action/UI advertising it unless that caller is updated. `bind_store()` starts inbox/outbox before setting `OPEN` and can report `OPEN` even after conversation attachment/restore fails (`gh-account-store.c:291–320`). Define gate activation after successful durable delegate attachment, gate revocation before unbind/cancellation, and what partial restore does; mere `state == OPEN` does not prove the once-only cache is usable.

### 3. Code-disproved, unnecessary, or simpler replacements

- **Relay transport description is overbroad.** `plan:45,75` says the existing scope/publish stack runs over libsoup; `gh-relay-net.c:78–107` uses GNostrRelay for `system`/`none` and libsoup/SOCKS for Tor. The correct claim is that the *installed network-mode dispatcher* enforces Tor; keep a real Tor-destination test. The fallback relay guard is a different build path (`gh-app-services.c:225–286`).
- **Blanket `wss://` validation conflicts with supported onion relays.** `plan:127` requires `wss://` outside test builds while also allowing `.onion` in Tor. The existing network policy accepts `ws://` for `.onion` in Tor and loopback, but rejects insecure clearnet `ws://` (`gh-net-session.c:54–78`). Reuse that policy for pasted bunker relays and editable pairing relays instead of inventing a stricter, inconsistent rule.
- **Periodic ping is not covered by permissions and is not required by the task.** `plan:141` requests five methods but omits `ping`; `plan:154` sends `ping` at connect and every five idle minutes. Either explicitly negotiate/support it and define denial behavior, or simpler, derive UI connectivity from subscription and real RPC outcomes without a periodic signer operation that may prompt an approver. Do not make successful ping the prerequisite for stored-history access.
- **Named helpers are real, not missing APIs.** `gh_account_describe_limits()` exists at `gh-account-controller.c:546–580`; `gh_account_store_continue_without_saving()` at `gh-account-store.c:769–784`. The plan correctly proposes changing their *policy/callers*, not creating replacements for nonexistent functions. Preserve the existing Grotto behavior while routing remote readiness through a backend-aware description.

### 4. Problems absent from both documents

- **Same npub, two backends share physical storage today.** Selection becomes `(backend,npub)` (`plan:96`), but the SQLCipher directory and key lookup are derived solely from the user pubkey (`gh-store.c:325–340,1656,1726`). Decide/document whether both signer rows intentionally share messages, seen IDs and cursor; if not, backend-isolated storage and migration are prerequisites. Do not casually change the store key: that would strand existing Grotto data.
- **First valid QR responder wins without user confirmation.** `plan:134–137` records any signer that knows the displayed bearer URI, obtains its `get_public_key`, then saves/selects it. A leaked/captured QR can race the intended signer. Add an explicit identity/relay confirmation before durable save, or state the accepted risk and what the UI displays; cancellation must close the listener while confirmation is pending.
- **Response/error taxonomy is too coarse.** `plan:87` maps every bunker `error` reply to `DENIED`, conflating user refusal with unsupported method, expired one-use token and authorization/login failure. Define retry/repair behavior per class without putting sensitive remote text in `GError`; a method-not-supported response should not silently imply the user denied it. Also decide whether a partial permission grant can be saved with clearly limited functionality.
- **Attempt/operation ownership is not fully specified.** A pairing dialog, per-account session, pending table, scope and one publish per relay all have independent async callbacks. Define one owner/main context, ref/cancellable handoff, generation checks before each completion, and teardown order for dialog disposal, account switch, network-mode switch and shutdown. Include a test where a late response arrives after credential save/cancel/switch; it must neither select a stale identity nor complete a new operation.

## Recommendations / design-changing questions

1. Is one remote signer per user pubkey intentional, including when the same pubkey is also in Grotto? This fixes both the credential schema (`plan:109`) and store-sharing policy before WI-2/WI-4.
2. Must protected signer relays support NIP-42 ephemeral AUTH during pairing and normal RPCs, or is a clear `auth-required` failure acceptable? Resolve before WI-1, since the scope/publish AUTH mode is per URL.
3. Is a human confirmation of the signer/user identity required before saving a scanned QR result, or is possession of the QR secret sufficient? Resolve before WI-5 UI/state tests.
4. Is `ping` an allowed/required permission and liveness signal, or should real request outcomes drive readiness? This changes the permission request and startup order.

**Version impact:** this review is documentation-only: no component bump. If WI-1 adds a public stateless API or splits the `nips/nip46` build target, assess that component separately under `VERSION_MANIFEST.md`; Groundhog's feature release remains its own version decision.

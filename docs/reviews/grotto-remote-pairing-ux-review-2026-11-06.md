## Owner-policy and regression checks

- **Single-use admission and reservation — confirmed/static and executed:** `bunker_service.c:434-450,522-524` matches the fixed-length random token and reserves the offer to one authenticated peer; a competing peer is refused. `connect_delivered()` marks the offer consumed, securely frees its secret and removes the offer (`:287-290`). The new getter reuses only an unconsumed, nonterminal, unexpired offer with matching identity and transport/security generations (`:982-999`). A consumed/expired offer is therefore not returned again. Fresh creation retains 32 random bytes, five-minute production TTL and the four-offer bound (`:924-964`). The full E2E reaches and passes its token reservation, consumption, second-peer rejection, cancellation, expiry and revoke assertions (`test-bunker-e2e.c:417-528`) before its later F1 failure. Accepted retries from the already paired peer are admission-only acknowledgements, not a second pairing or a signing grant.
- **Regeneration and honest UI — confirmed/executed:** `signer/remote-signing` exercises the real daemon, Control1 adapter and production panel bridge. It verifies that repeated requests reuse the displayed offer, then observes a different link after consumption while the relay still withholds the original connect response's `OK` (`test-bunker-e2e.c:761-796`). Releasing `OK` completes the original durable pairing; creating the replacement does not cancel that transaction. The old secret was already consumed, not merely hidden. The description says single-use links are replaced after an app connects; there is no misleading manual Regenerate action. Merely closing/reopening the shared display is **not cancellation or rotation**: an unused link remains valid until use, expiry or explicit invalidation. Switching identities can retain separate unconsumed offers within the existing bound; it does not claim to revoke an earlier identity's offer.
- **Disabled / not Ready / stale responses — confirmed/static and executed:** the panel requests only when mapped, remotely enabled, `LISTENING` and command-capable; it clears the URI outside Ready and on unmap (`gnome/grotto-panels/src/grotto-remote-panel.c:144-171,194-197`). The trusted bridge fences replies by mapped/capability/owner generation and discards superseded replies using its dirty flag (`apps/grotto/src/grotto-connection-link.c:8-39`). The daemon also rejects disabled, unhealthy, paused, headless or non-running issuance (`grotto_control.c:910-921`; `bunker_service.c:983-984`). The QR sheet clears data on unavailable/not-listening status, identity change, expiry, close and owner disappearance; pending refreshes are coalesced (`sheet-qr-display.c:105-129,291-383`). Panel and sheet fixtures pass disabled/starting/ready and identity-choice cases. Refresh is asynchronous: a previously rendered link can remain visible briefly until the status/getter round trip finishes; this is not a claim of instantaneous pixel removal. Its consumed secret cannot create another pairing server-side. Arbitrarily delayed D-Bus delivery was source-reviewed, not fault-injected.
- **Settings manager gets no link — confirmed/static and executed:** Control1 authorizes before dispatch, explicitly excludes managers from approver inheritance, and uses a closed manager allowlist that does not contain `GetConnectionLink` (`grotto_control.c:720-728,768-783`). `test-control-untrusted.c:21,53` adds explicit manager and untrusted denial checks. `signer/clients` passes the untrusted path. A separate serial `signer/approval-integration` run passes the actual manager helper path (`test-approval-integration.c:788-791,810,825,831,935-936`): the helper verifies its `manager` role and receives `NotAuthorized` for `GetConnectionLink` before its permitted label mutation. Manager-readable status/client snapshots do not include the URI/token. The Settings host does not install the Grotto-only bridge; an insensitive display/QR action is not an alternate secret RPC.
- **Panel custody boundary — confirmed/static and executed:** only Grotto's trusted host calls `GetConnectionLink` and supplies the transient shareable URI to the additive setter; the production binding is in `signer-window.c:896-905`. No panel D-Bus, credential-store, account/transport-key or policy-evaluator access was added. The URI contains a bearer pairing token and is sensitive display data, not an account key; this host-supplied display is the owner's explicit current exception to the older blanket no-token panel wording. It is not inserted into shared metadata/status models. Panel clipboard ownership is cleared when the URI changes, on unmap and disposal (`grotto-remote-panel.c:120-143,212-216`); the sheet similarly clears its own clipboard content and wipes its payload. Neither implementation promises erasure of copies already taken by an external clipboard manager. `no-secrets` passes its closed imports/exports, admission and negative-mutant checks. The focused real-daemon E2E also checks both original and replacement token/URI values against daemon/restart logs (`test-bunker-e2e.c:766-770,790-792,1313-1325,1426`); this is not a process-wide memory-forensics claim.
- **Account/transport separation and permissions — confirmed/executed and static:** the remote-signing E2E obtains the configured account public key, asserts it differs from the transport key, verifies the returned account signature, and verifies pairing/config persistence across restart (`test-bunker-e2e.c:799-837`). Client-supplied `perms` still enter the common gate as display hints, never a grant (`bunker_service.c:530-549`); new pairing still requires explicit review. Headless behavior passes independently and remains negative-only for review-required work. Token-paired revoke defeats cached connect replay in the full E2E prefix (`test-bunker-e2e.c:472-476`); F1 prevents a general claim that all rejected-envelope replay protection works.
- **Multiple identities — confirmed/static plus fixture execution:** the daemon resolves an explicit choice, then its ephemeral connection-display choice, then configured default; with none it auto-selects only exactly one stored signing identity (`grotto_control.c:661-680,693-695,918-919`). The QR sheet hides the chooser for one identity, shows it for multiple, sends an explicit selection and reconciles the returned identity (`sheet-qr-display.c:304-315,341-346,385-407`). It does not change the account default or grant policy. The passing layout fixture exercises choosing another identity and reopening with that display choice. The real-daemon E2E uses one account; two real stored accounts were not exercised end-to-end. The panel URI names the transport key, not the account: use Show QR Code to inspect/change the associated identity, rather than inferring an account from that URI.
- **Connected Apps / safe relays — confirmed/static and executed:** the daemon enumerates explicit client fields and relays, not connection secrets (`grotto_clients.c:276-305`). The adapter admits only validated relay URLs (`grotto-panels-control1-service.c:70-81`); the Control1 fixture supplies a credential/query-bearing URL followed by a safe relay and checks that only the safe relay crosses (`gnome/grotto-panels/tests/test-control1.c:29-33,151-156`). Paste opens the parsed remote-client preview, not silent admission. Open Link File, runtime/status and local-app copy are removed. `host_add_app()` uses the Cancel-only header and no bottom action stack (`signer-window.c:834-846`; `dialog-actions.h:6-21`); the retired create-bunker sheet is removed from resources and both build inventories.

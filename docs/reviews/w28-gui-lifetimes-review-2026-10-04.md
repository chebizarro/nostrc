**Verdict: CHANGES-REQUIRED** on `groundhog/w28-gui-lifetimes` at `22ef88d3` (base `origin/master` `cf616c3d`). Review branch: `review/w28-gui-lifetimes`. This is a review, not a change to the author's worktree.

## Findings

1. **High — The completion-jitter harness is neither seeded nor broad enough for its advertised suites.** `gnome/groundhog/src/mls/gh-mls-invitee.c:55-72`, `scripts/test-groundhog-gui-lifetimes.sh:9-12`. `GH_TEST_ASYNC_JITTER_MS` is only an upper bound; there is no seed input or replayable schedule. Delays derive from a process-global atomic serial whose assignment depends on completion order. More importantly, the delay is inserted only in `gh_mls_invitee_check_async()`'s lookup completion. The menu and clipboard completions are not jittered by this script, although `groundhog-conversation-menu-gui`, `groundhog-composer`, and `groundhog-attachment-ui` are advertised as stress targets. Their tests run, but ordinary repeats cannot exercise a deliberately delayed menu notification or paste callback. A timing regression in either path can therefore pass every stress round. Add explicit, seeded completion control to the relevant paths (or describe and name the narrower MLS-only scope), and assert in tests that each injected completion actually occurred.

2. **High — No regression presently proves the MLS picker lifetime fix.** `gnome/groundhog/src/ui/gh-mls-invitee-picker.c:175-212`, `gnome/groundhog/tests/ui/test_mls_ui.c:1714-1790`. The weak references, cancellation and dispose guard are real hardening, but the `new-group-formats` test waits for each lookup to finish before teardown; it does not force a completion after a row/picker is removed. With the picker production file restored to its pre-fix `origin/master` version while retaining the new tests and jitter, `groundhog-mls-ui-gui` passed, and all four harness suites passed four more repeats at 50 ms. This does **not** show the new code is wrong; it shows the claimed regression/stress evidence cannot distinguish the old vulnerable path. Add a targeted in-flight teardown test that fails against the old picker and passes with weak references/cancellation.

3. **Medium — The configure/CI/pre-push GUI-tolerance check is bypassable.** `scripts/check-gui-test-gdk-frame.py:13-23,61-71`. The regex strips `//` without recognizing C string literals. I added a temporary, otherwise valid GUI test under `gnome/groundhog/tests/ui/` with no tolerance header or call; placing `const char *url = "https://example.invalid"; gtk_test_init(...);` on the same line made the checker report success and still count only 30 existing sources. Its own control probe, a straightforward test lacking the header, was rejected. A newly added GUI test can therefore reach all three gates with the GTK skipped-frame warning still fatal. Use string-aware lexing or a source-independent target/CTest manifest check; add a self-test for this case and for init hidden behind a helper.

## Fix assessment and evidence

- **Conversation menu:** `gh-conversation-menu.c:44-47,467-492,578-583` binds stack/view notifications through `g_signal_connect_object()` to the window, looks up attachment data only while live, and disconnects the shown-conversation notifications at window destruction. This is a lifetime fix, not a null-check band-aid. The new `header-menu-lifetime` test segfaulted (exit 139) with only the menu production file reverted, then passed after restoration. It plausibly explains a later `blocked-page` failure if a prior test leaves a child widget alive after its window, but the named `20261003T175322Z-7-first-run.log` was absent from the supplied Docker volume, so that exact gate stack/timing could not be verified.
- **Clipboard:** `gh-composer.c:498-573,668-674` gives each read a cancellable and a weak composer reference, cancels superseded/disposed reads, and refuses to signal after disposal. This is a real lifetime fix. `paste-after-close` failed against the pre-fix composer (fatal invalid `GhDmInbox` assertion; exit 133) and passed after restoration.
- **MLS:** Picker/row callbacks now acquire strong references from weak refs and verify cancellation/ownership before touching widgets; the new-group and group-info callbacks reject completion after dispose. This is plausible hardening for the `new-group-formats` gate failure, but the available `20261004T035431Z-7-first-run.log` shows only `object_ref: !object_already_finalized` at that test, not a stack implicating these callbacks. The missing targeted regression leaves the causal claim unproven.
- **GTK warning tolerance:** Existing touched tests use the narrow `nostrc-test-gdk-frame.h` helper; the policy is test-only. The manifest's no-additional-bump decision is appropriate: the Groundhog production fixes are PATCH-class within unreleased `0.12.0`, and the other changes are test/build checks.

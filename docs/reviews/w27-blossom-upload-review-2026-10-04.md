## Required findings

1. **Medium — suggest compatible encrypted-media servers in the first-use sheet.** `gnome/groundhog/data/ui/gh-attachment-sheet.blp:47-55` warns that image-only servers may refuse ciphertext, but offers no compatible example; `gnome/groundhog/data/org.nostr.Groundhog.gschema.xml:142-145` deliberately defaults the list to empty. A first-time user following the sheet must guess a URL and can choose `blossom.nostr.build` or `blossom.primal.net`, reproduce HTTP 415, and still be unable to send a Groundhog file to a White Noise contact. MDK 0.11 lists `https://blossom.divine.video`, `https://blossom.ditto.pub`, and `https://cdn.hzrd149.com` for *encrypted* media (`/tmp/mdk-v0.11.0/crates/marmot-app/src/media/mod.rs:186-203`); primal is its *public profile image* default. Suggest compatible options without silently selecting or contacting one, preserving the charter's explicit server choice. This is required for the stated Groundhog↔White Noise first-use outcome, not a request to add an automatic default.

2. **Medium — model content-sniffing refusal in the Blossom fixture.** `gnome/groundhog/tests/media/blossom-fixture.c:127-135` makes `strict_upload` require `application/octet-stream`, then makes `reject_opaque` reject solely when the *declared* Content-Type is octet-stream. That is not the observed image-only policy: in a live, valid kind-24242 probe, primal returned HTTP 415 for opaque ciphertext declared `image/png`, and nostr.build returned HTTP 400 (`Content-Type header does not match the file content`). With `strict_upload` off, this fixture would accept those same opaque bytes if a client spoofed `image/png`; with it on, the fixture produces a synthetic 400 before its 415 policy. Thus `/groundhog/blossom/strict-encrypted-upload` and `/groundhog/attachment-ui/opaque-server-refusal` exercise status propagation, but do not prove the real policy or prevent a future plaintext-MIME spoof workaround. Keep the useful BUD-11 conformance mode, but make the refusal mode inspect body bytes independently of the MIME header and test the spoof case.

## Verified behavior and limits

- [BUD-11](https://github.com/hzrd149/blossom/blob/master/buds/11.md) explicitly requires URL-safe Base64 **without padding**. The old `g_base64_encode()` output was nonconforming when its token contained `=`, `+`, or `/`; the new encoder is correct. This was **not demonstrated to be the cause of HTTP 415**: a fresh signed probe with padded standard Base64 was accepted by divine (200), ditto (201), nostr.build for a valid PNG (201), and primal for that PNG (200). The matching unpadded probe also succeeded on the first three; primal returned 400 `invalid base64 for auth event` for that particular padded-requiring token. Exact server behavior is therefore mixed and the strict fixture must not be described as what those servers universally enforce. For a Groundhog-shaped opaque PUT, nostr.build returned 415 with both encodings. This finding does not argue for reverting the BUD-11 fix.
- `gh-blossom-client.c:439-456` sends the ciphertext as `application/octet-stream` with `X-SHA-256` equal to the ciphertext hash; `gh-net-http.c:631-640` puts that header on the request. [BUD-02](https://github.com/hzrd149/blossom/blob/master/buds/02.md) permits that hash header and defines 415 for unsupported blob types. The event has `t=upload`, ciphertext `x`, `expiration`, and lowercase-domain `server`, with **no `size` tag** (`gh-blossom-client.c:186-208`). MDK 0.11's `blossom.rs:354-395,1480-1512` has the same essential method, MIME, hash header, auth encoding and tag set. This is semantic parity, not byte-for-byte identical: Groundhog also sends `Accept: application/json`, signs content `Upload file` with a 300-second lifetime and a different tag order; MDK signs `Upload Blob` with a 600-second lifetime. None is a BUD incompatibility.
- The sheet path passes its current GSettings list into this upload (`gh-attachment-ui.c:380-417`); `upload_start()` duplicates that list into the task at `gh-blossom-client.c:590-594`. It does **not** set `servers_override`, so a concurrent Preferences/default upload independently reads its own list. `on_sheet_server()` persists a successful first-use choice to GSettings (`gh-attachment-ui.c:431-450`), and the existing first-use test verifies it. The new live-choice test verifies a deliberately stale shared override cannot redirect this send. The test is not itself a simultaneous-transfer stress test, but the per-task ownership removes the relevant shared-list race.
- For ordinary NIP-17 uploads, `gh-blossom-client.c:503-526` signs with a fresh generated key unless that normalized server has per-server account consent; the existing consent test observes the throwaway-key first attempt and account-key retry. Keyed MLS group-image uploads deliberately use their separate blob owner key. No unconsented account signature path was introduced.
- The revised sheet copy accurately states that ciphertext is uploaded and that image-only servers may refuse it. The charter's server-refusal text is appropriately conditional. The HTTP 415 body remains visible in the sheet rather than being called an encryption failure or “no server.”
- `VERSION_MANIFEST.md:239` contains the slice-G groundhog decision **inside** the component decision table. PATCH-class fixes are folded into the already-unreleased `0.12.0`, with no separate bump. There are no new test binaries; the modified `groundhog-blossom` and `groundhog-attachment-ui` binaries are CTest-registered and included in hosted CI (`.github/workflows/groundhog-ci.yml:84-87,130-133`).

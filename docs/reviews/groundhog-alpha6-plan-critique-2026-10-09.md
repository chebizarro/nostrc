# Groundhog alpha-6 plan: focused critique

## Context / scope

Compared `docs/plans/groundhog-alpha6-2026-10-09.md` with **only the generated response** under `## Generated Plan` in `prompt-exports/oracle-plan-2026-10-09-001607-groundhog-alpha-6-re-a681.md`; the export's prompt and file inventory are context, not a second specification. Spot-checked the named APIs and current code. The plan's retention of persisted per-contact picture consent is the owner's deliberate correction, **not** a defect. No implementation was changed.

## Findings

### 1. Export content missing or weakened

- **None found.** Apart from that consent correction, the plan carries the generated response's implementation-bearing contracts through §6 and adds an execution index and investigation appendix. Do not restore the export's picture-grant clearing, session-only authorization, or associated migration row (`export:172,242,265`; `plan:90,182`).

### 2. Under-specified seams, contradictions, and wrong references

- **NIP-34 commit tags are wrong.** The proposed `64-hex e` references (`plan:119,153`) confuse a Nostr event ID with a Git commit ID. [NIP-34](https://raw.githubusercontent.com/nostr-protocol/nips/master/34.md) uses `e` for Nostr events and `r`/commit-specific tags for Git commits; its issue form does not define related-commit `e` tags. Decide whether related commits are body text or an explicitly documented extension, and accept the repository's Git object format rather than assuming 64 hex. The header is already known: `nips/nip34/include/nip34.h:220–245`; replace `include/**/nip34.h` and the “check path later” note (`plan:153`).
- **dbusmenu needs a wire contract, not merely a snapshot type.** `GetLayout` has recursion depth and property-name filters; `GetGroupProperties` also filters; separators use `type=separator`, checkmarks use string `toggle-type` plus **integer** `toggle-state` ([Canonical-authored DBusMenu XML](https://github.com/gnustep/libs-dbuskit/blob/master/Bundles/DBusMenu/com.canonical.dbusmenu.xml)). Current code ignores those inputs and invents properties for unknown IDs (`gnome/common/gn-status-notifier.c:45–176`). Specify valid-ID/error behavior for every method, property filtering, revision/signal ordering, and `EventGroup` error IDs. `Event` carries no revision, so “stale item” cannot be detected by revision: validate the ID against the current immutable snapshot or retain explicit retired IDs. Test a real host re-query after `LayoutUpdated`, not just emitted signals (`plan:96–106`).
- **Background API/migration is not yet a coherent state machine.** `gh_background_set_launch_on_login_async()` is proposed, not present; existing `gh_background_set_enabled_async()` immediately writes `run-in-background`, whose explicit user value currently *is* the autostart choice (`gh-background.h:21–46,113–127`; `gh-background.c:779–808`; gschema `:133–138`). Define two independent getters/setters and one serialized reconciliation owner, including what happens if background is disabled while launch remains on, a portal grants background but denies autostart, a host autostart file was manually disabled, or a newer choice arrives before an older callback. The current portal failure path can turn background off (`gh-background.c:299–329`); copying that rollback blindly would erase the new independent preference (`plan:107–111`).
- **History paging has no continuation seam.** The current `GhRelayScope` pages only the startup backfill round, reports one aggregate URL-level EOSE plus `incomplete`, and has no “next older batch” call (`gh-relay-scope.h:58–90,181–192`). `GhNip29Service` uses one live scope per relay and a group identity that already includes relay URL (`gh-nip29-service.h:18–41,92–97`). Specify a separate historical REQ/scope or an extension that preserves live traffic, its exact per-group persisted key/transaction boundary, and how UI demand resumes after the 16-page cap without restarting from the newest page. Do not commit an “oldest” position from a page merely because the scope's final EOSE arrived; distinguish empty, failed, capped, offline and same-second-ambiguous outcomes (`plan:72,159,182`). First prove whether the reported bug is fetch or list insertion before committing to a schema migration.
- **The portable target split must name symbol ownership and both build systems.** `gn_content_parser` is already an OBJECT library embedded in `nostr_gtk`, which also holds Gnostr-coupled sources; moving/copying parser objects into another target without a link/export plan risks duplicate symbols or lost legacy ABI (`nostr-gtk/CMakeLists.txt:113–180,197–239,352–374`). Specify one owner for each public symbol, old-target transitive linkage, installed pkg-config/CMake/GIR behavior, and Meson parity (`nostr-gtk/meson.build:89–105`). The plan's Groundhog 4.14/Adw 1.5 ceiling (`plan:169`) is not the library's compatibility floor: nostr-gtk currently requires GTK **4.6**/Adw **1.2**, while Groundhog requires **4.14**/**1.5** (`nostr-gtk/CMakeLists.txt:40–43`; `gnome/groundhog/CMakeLists.txt:17,173–175`). New portable APIs must either work at the lower floor or explicitly change the library's advertised minimum and package requirements.
- **Issue review must freeze the actual event inputs.** Today the dialog snapshots fields, previews a hand-built description, then constructs the unsigned event only *after* consent (`gh-issue-dialog.c:119–137,145–213`). “Exact final body/tags” (`plan:125,206`) needs one canonical draft/event-tag builder used by both preview and publish; editing any structured field or changing diagnostics opt-in must invalidate it. Define length checks on the *assembled* UTF-8 body, not just the original body, and preserve the current generation/cancel/partial-OK paths (`gh-issue-dialog.c:35–104,218–241`).
- **Version work is a missing dependency.** The plan adds public nostr-gtk and NIP-34 APIs but has no component-version decision. `VERSION_MANIFEST.md:17,21,25` lists nostr-gtk **1.0.1**, Groundhog **0.12.0**, NIP-34 **0.1.0**; repo policy requires a per-component assessment and synchronized CMake/Meson source and manifest values. A compatible new nostr-gtk public API is at least a MINOR candidate; decide before B1, not at release packaging. This review itself is documentation-only: no bump.

### 3. Details code disproves or a simpler design replaces

- **OG data is already parsed locally, but image metadata is not.** `GhWebContent` already fetches consent-gated HTML and extracts title/description; `GhWebResult` has no `og:image` URL, and the parser deliberately discards it (`gh-web-content.c:58–100`; `.h:7–17`). Port only the app-independent *presentation* card if that suffices; if alpha-6 promises OG artwork, first add an inert image-URL result and a separate explicit load action. Do not import Gnostr's network service into Groundhog (`plan:87–88,165`).
- **“Promote” understates Markdown work.** Gnostr's `markdown_pango.c` is a direct Markdown-to-Pango converter, not the bounded token/document API promised in `plan:79–84` (`apps/gnostr/src/util/markdown_pango.c:87,259,379`). Treat the parser as a new implementation with compatibility fixtures for the existing Gnostr wrapper, not as a source move. Groundhog currently formats the body directly during row bind (`gh-message-row.c:887–901`); its `GhMessage` body is immutable, with no body-revision API (`gh-message.h:30–51`). Key a cache by account/message identity plus only actual mutable presentation dependencies, rather than inventing a revision field.
- **Copying “original body” can reveal a file URL rather than the visible message.** For a kind-15 file, content is its URL while `gh_message_dup_display_text()` intentionally shows “Photo”/“File” (`gh-message.h:64–74`). Clarify whether Copy Message means visible text, authenticated raw content, or a separate Copy Link action; include withdrawn/expired/recycled rows and a clipboard test. The plan's generic “authenticated original body” is not neutral (`plan:92`).

### 4. Requirements and edge cases absent from both

- **Async ownership and opt-out races:** name the owner/main context and strong/weak refs for a row's worker parse, OG fetch, gallery load, tray callback, diagnostics write and issue publish. On unbind, account switch, window/dialog teardown and shutdown, cancel then reject late results by generation; an in-flight diagnostics write must not recreate files after Disable/Delete. Test late callbacks and disposal, not just synchronous setters. Keep existing persisted picture grants; cancelling a fetch does not revoke that consent (`plan:82–92,113–126`).
- **Conversation-open performance is the relevant gate.** The generic nostr-gtk latency test is not a Groundhog Markdown row-bind test (`nostr-gtk/tests/test_bind_latency_budget.c:215–289`; `plan:178,211`). The recent mapped 1,000-message A→B→A investigation found ~205 row setups and ~615 message-row measures before first paint, with label measurement nested in ~60 ms of view measure (`docs/analysis/groundhog-persistent-list-gate-2026-10-08.md:6–26`). Measure cold/warm open and switching with real Markdown, cache misses, long bodies and recycled rows using Groundhog's existing conversation-view probe (`gnome/groundhog/CMakeLists.txt:1309–1327`); bound work *before* first paint, not only average steady-state bind CPU.
- **Testability of the new boundaries:** use a fake dbusmenu watcher/portal, deterministic relay page transport, counting HTTP transport and injected diagnostics filesystem/clock; assert no network on widget construction/bind/navigation, no writes before opt-in or after opt-out, and no helper-only success. These follow the plan's release claims but are not yet tied to injectable ownership/interfaces (`plan:71–74,85–88,113–126,204–213`).

## Recommendations / design-changing questions

1. Does “full NIP-21/18” require only reference/repost *display* in Groundhog, or also composing/publishing reposts? The plan chooses display-only (`plan:39,84`); a different answer changes B1/B2 and acceptance.
2. For Copy Message, should kind-15 and withdrawn content copy exactly what is visible, expose the underlying URL/body, or disable copying? Decide before B2's action and tests.
3. Are named native reviewers available for **all eight** catalogs, and are all five package formats hard alpha-6 gates? The plan makes both release blockers while leaving reviewers and package manifest inventory unresolved (`plan:173–177,197–213,218–220`); a different answer changes D1/E1 order or the release cut.

behaviour is genuinely exercised: `big.bin` uploads as **4 × 256 KiB** sealed

### (a) PINNED / CACHED READ — zero network traffic

**PASS** (with a design-vs-implementation caveat, see "Observed gaps" below).
After case (b) the cache holds all 8 blobs. An `nft` rule was installed on the
VM's OUTPUT chain to drop every packet destined for the Blossom server's TCP :443:

```
$ sudo nft -f - <<'NFT'
table inet fuse_smoke_1u55 { chain out { type filter hook output priority 0;
  ip daddr 192.168.40.104 tcp dport 443 counter drop; } }
NFT
$ time sha256sum mnt/big.bin
cc9d9defded6c118b6328ae910ef8049925c2761e498504804eacd8787dee3f7  mnt/big.bin
real   0m0.016s
$ time sha256sum mnt/medium.bin  # 0m0.004s
$ time sha256sum mnt/small.txt   # 0m0.004s
$ sudo nft delete table inet fuse_smoke_1u55
```

Every read completed under 20 ms with Blossom unreachable — proof the reads
were served from tier 1 (in-process plaintext LRU, populated by case b) and/or
tier 2 (local sealed-blob cache), never touching the network. The nft counter
after the reads showed 0 packets to the Blossom IP.

Design gap flagged: the mount does not wire `nh_syncd_pin_ring_open` /
`_apply` (design §3.3). Practical impact: nil for a mount that never sweeps —
which this mount does not. Filed as an observed gap.

### (g) EROFS — every mutator refused

**PASS.**

```
touch    → Read-only file system (EROFS)
mkdir    → Read-only file system (EROFS)
rm       → Read-only file system (EROFS)
rmdir    → Read-only file system (EROFS)
mv       → Read-only file system (EROFS)
chmod    → Read-only file system (EROFS)
chown    → Read-only file system (EROFS)
truncate → Read-only file system (EROFS)
ln -s    → Read-only file system (EROFS)
ln       → Read-only file system (EROFS)
setfattr → Read-only file system (EROFS)   [kernel VFS ro pre-empts nhf_setxattr's ENOTSUP]
> (write via O_WRONLY on existing)  → EROFS
> (create via O_CREAT)              → EROFS
os.open O_WRONLY               → EROFS
os.open O_RDWR                 → EROFS
os.open O_WRONLY|O_APPEND      → EROFS
os.open O_WRONLY|O_TRUNC       → EROFS
```

`setxattr` returns EROFS rather than ENOTSUP because the kernel VFS
short-circuits any write path on a `-o ro` mount before reaching the FUSE
op. That is a strictly stronger negative and preserves the design's
"read-only, no side-effects" invariant.

`$HOME` outside the mount stayed writable (touch + rm confirmed on
`$HOME/.fuse-outside-write-test`). `snapshot.json` was byte-identical before
and after the whole EROFS sweep (`sha256sum` reproducible at
`7a2d5060c4057fb7dacac87f1ca3a6a31edf5b17ba544b12b1ae7e920413d788`).

### (h) LAZY SUBTREE — mount serves matching prefix from Blossom on demand

**PASS.**

Two-part proof:

1. **Mount-side (live).** With `NOSTR_HOME_STATE=partial` the mount's tier 0
   ($HOME pread) is disabled, so every read walks tier 2/3 — this is the exact
   shape a lazy-subtree entry produces (chunk addresses recorded, no eager
   bytes on disk). Cache wiped, mount started against the gen-2 snapshot,
   `subdir/nested.bin` read via the mount:

   ```
   sha256(mnt/subdir/nested.bin) = 1f6045c353…  == fixture/subdir/nested.bin
   readlink mnt/subdir/link_to_small          = ../small.txt
   $XDG_CACHE_HOME/nostr-homed/blobs/…/92659525…   (freshly written to disk,
                                                    proves tier-3 → tier-2
                                                    populate happened)
   ```

2. **Syncd-side (unit tests).** The additive-only interlock — "record in
   snapshot, do not materialize; delete-remote does not delete-local for
   matching entries" — is covered by two ctest cases that live under
   `NOSTR_HOMED_ENABLE_SYNCD_EXPERIMENTAL`:

   ```
   Start 179: homed_syncd_lazy
   1/2 Test #179: homed_syncd_lazy .................   Passed    0.00 sec
   Start 180: homed_syncd_lazy_reconcile
   2/2 Test #180: homed_syncd_lazy_reconcile .......   Passed    0.02 sec
   100% tests passed, 0 tests failed out of 2
   Labels: nostr-homed;porthome;portable-fuse;portable;syncd
   ```

   These exercise `nh_syncd_lazy_covers` and the reconciler's suppression
   points (`nh_syncd_reconcile.c:990` for remote-changed materialization and
   `:1121` for remote-delete). Design §10 additive-only contract holds.

## Observed gaps (implementation vs design)

These are consequences of the current code shape at `4ba48227`, not
regressions introduced by this smoke. None caused a case to *fail* per the
task's acceptance bar — reads never returned wrong bytes, writes never
succeeded, and the mount never wedged — but they are worth naming so a future
maintenance pass can close them. Every one is larger than a "one-line-obvious"
fix, so per the task constraint I have left them unchanged.

1. **`fuse-status.json` reports `"mounted":false` always.** The global
   `g_session` in `src/porthome-fuse/nostr-home-fuse.c` is declared but never
   assigned (`fuse_get_session()` on the running fuse handle would populate it
   in `nhf_init` or after `fuse_main` starts). The rest of the file — schema,
   generation, counters, `last_miss_epoch` — is correct. Impact: monitors that
   read `mounted` see `false` even while the mount is live. Design §6.2
   specifies this file as the health seam for `systemctl --user status`.

2. **Inotify-driven snapshot reload not wired.** Design §7.3 D10 and §13 F4
   call for an inotify watcher on the state dir that debounces 500 ms, swaps a
   new table in on `IN_MOVED_TO` of `snapshot.json` / `generation`, re-applies
   the pin ring, and issues `fuse_invalidate_path` per changed entry. The
   current code declares `<sys/inotify.h>` but starts no watcher; the table is
   loaded once at mount time and never rebuilt. Impact: `open()` on the same
   path across a generation change returns the *old* content until unmount +
   remount. Per-open pinning (§7.3, `fi->fh` snapshotting `entry` at open time)
   works correctly.

3. **Tier-2 AEAD failure does not fall through to tier 3.** Design §3.1's
   tier-3 line is "populate tier 2 (re-verifies), decrypt, insert into tier
   1"; §3.3 says a pinned blob that only misses tier 2 due to on-disk
   corruption "is treated as a tier-3 fetch, not as an error". The current
   `nh_fuse_source_chunk` returns `-EIO` immediately when
   `nh_porthome_decrypt_chunk` fails on tier-2 bytes; it does not attempt
   tier 3. Impact: cache corruption is terminal EIO on that chunk until the
   cache entry is manually cleared or overwritten. The critical safety
   property — "corrupt cache never emits wrong plaintext" — is preserved.

4. **Pin-ring not wired at mount.** Design §3.3 requires
   `nh_syncd_pin_ring_open(default_pin_path)` + `_apply(cache)` after loading
   the snapshot (and again on every generation reload) so blobs referenced by
   the last N generations are refcount-protected. The mount does neither.
   Practical impact today: nil, because the mount never sweeps
   (`nh_syncd_cache_sweep` is only called by syncd) — the pin ring is
   effectively still applied by syncd out-of-band. If the mount ever gains a
   sweep path (or shares a cache with a daemon that does not run in lockstep),
   this becomes load-bearing.

5. **Offline budget is per-chunk, not per-read.** Design §6.1 reads "5 s
   connect / 15 s total across the whole server list". The current mount
   passes `timeout_seconds=15, max_retries=1` to the Blossom client per
   chunk and explicitly declines to layer an aggregate budget on top (the
   comment in `nh_fuse_source.c` names the reason: "double-budget bugs").
   Observed behaviour: a 4-chunk file with tier 2 empty and Blossom
   unreachable returns EIO in **62 s**, i.e. ~15 s per chunk. Bounded and
   terminal (never a hang), so the design's "no indefinite block" invariant
   holds — the wall-clock ceiling grows linearly with chunk count rather
   than being 15 s flat. Acceptable to document; changing it would need a
   maintainer decision on per-read vs per-chunk semantics.

## Test-only additions this run introduced

Two small pieces of code are added to the source tree so the live smoke has a
repeatable operator harness. Both are gated behind existing experimental
options — they cannot land in the base package.

1. **`gnome/nostr-homed/tests/integration/porthome_fuse_fixture.c`** (new). An
   operator tool that walks a fixture dir, encrypts + uploads sealed chunks to
   a real Blossom server (BUD-02 signer using a real nsec, matching
   `nostr_home_publisher.c` shape), signs and publishes a kind-30078 pointer
   to a real relay, and writes a full `snapshot.json` under `--state-dir`
   with every field the FUSE mount consumes (kind, mode, uid, gid, mtime_ns,
   size, `content_hash_hex`, `chunk_addrs_hex`, `symlink_target`) and the
   snapshot schema header (`schema=1`, `generation`, `root`, `d_tag`,
   `account_pubkey_hex`, `root_id_hex`, `files`). Accepts `--generation` for
   re-publishing at gen 2 (used by case f). Accepts `--chunk-size` to work
   around the sharegap.net PUT ceiling (documented above). Not a CTest case —
   registered as a target only under
   `NOSTR_HOMED_ENABLE_PORTHOME_FUSE_EXPERIMENTAL + NOSTR_HOMED_BUILD_TESTS`
   in `gnome/nostr-homed/CMakeLists.txt`.

2. **`NH_FUSE_CHUNK_SIZE` env override on the mount.** Two-line addition in
   `nhf_read` reading a `strtoull` value in `[4096, 4194304]` and defaulting
   to 4 MiB. Same rationale as (1): matches the fixture's chunk size on rigs
   whose Blossom PUT ceiling forces a smaller sealed-blob size. In production
   the env var is unset and the design's 4 MiB chunk size stands.

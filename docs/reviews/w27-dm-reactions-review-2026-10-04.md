## Findings

1. **High — a nonparticipant's reaction appears in another DM.** `gnome/groundhog/src/app/gh-app-outbox.c:304-309`, `gnome/groundhog/src/app/gh-reaction-store.c:157-169`, `gnome/groundhog/src/store/gh-store-reactions.c:60-80`, `gnome/groundhog/src/ui/gh-conversation-view.c:1817-1827`. The new receive path computes C+A for a reaction from C addressed to A, but admission still indexes the in-memory summary only by the target rumor ID. If C knows an A–B rumor ID and sends a reaction to A, `delegate_admit` treats C+A as an unknown room and returns success; the summary then updates A's open A–B bubble. I reproduced this with a temporary three-account extension of `groundhog-e2e-dm`: C's `x` chip appeared on A's A–B message, while no C reaction row was stored under A–B. Reject or defer a reaction until the target message is verified to belong to the computed room, or key summaries by both room and target; add a permanent negative regression.

2. **High — the new store regression is absent from Groundhog CI's build/required lists.** `.github/workflows/groundhog-ci.yml:54-76,94-128,135-144` versus `gnome/groundhog/CMakeLists.txt:367-371`. `test-groundhog-e2e-dm` is listed, but `test-groundhog-reactions` is not built or required (nor in the sanitizer set at workflow lines 197-215). CI nevertheless runs every registered `groundhog-*` CTest, so a clean focused CI build leaves `groundhog-reactions` as **Not Run** and fails; the new empty-summary regression is never executed there. No new binary was introduced, but the newly changed existing binary must be included in the workflow's build and required sets, and in sanitizer coverage if its store/model logic is intended to be sanitizer-gated.

3. **Medium — rapid same-emoji off/on cannot restore a reaction.** `gnome/groundhog/src/app/gh-outbox.c:2073-2093`, `gnome/groundhog/src/app/gh-app-services.c:700-713,743-751`. A kind-7 rumor ID is deterministic from its contents and whole-second `created_at`. After a reaction is deleted, re-adding the same emoji to the same target in that second recreates the same ID; `gh_store_enqueue` fails the `(conversation_id, backend_msg_id)` uniqueness constraint and the UI path ignores the error. A temporary two-account delete/re-add probe reproduced the constraint error. This predates the patch, but the requested toggle behavior remains broken. Use a fresh unique event timestamp/identifier without violating NIP-01, and regression-test a quick off/on.

4. **Low — the branch does not cherry-pick cleanly onto current master.** `VERSION_MANIFEST.md:232`. `git cherry-pick --no-commit 74c3dbeb` onto master `3e3ef4d0` conflicts in the decision table because master has additional W27 rows at the same insertion point.

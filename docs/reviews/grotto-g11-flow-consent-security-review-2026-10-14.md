# G11 flow-consent security review

## Context / Scope

**Verdict: REQUEST CHANGES.** Pause does not invalidate flow consent. Failed revocation also retains consent, and the new API inherits the documented UID-only-bus caller/approver weakness. Principal/identity/transport/exact-kind isolation, count limits, and non-persistence otherwise have a sound source-level boundary on PID-verified callers. Same-principal “only this send” isolation is weaker than the UI wording suggests.

## Findings (severity order)

### F1 — High · Confirmed: flow consent survives pause/resume

- **Location:** `nips/nip55l/src/glib/signer_approval_service.c:1308-1317`; `nips/nip55l/src/glib/signer_permissions.c:31-37,458-477`; production entry point `apps/grotto/daemon/grotto_control.c:691-699`.
- Pause increments the service generation and cancels extant requests, but never removes `permissions->flows`. A `Flow` has no generation fence. Resume returns without further invalidation; a **new** request gets the new service generation and can consume an unused slot from the old grant. Execution is blocked while paused, but consent becomes usable again afterward.
- **Local reproduction:** against the rebuilt branch library, create a three-slot required-seal consent, consume one slot, call `signer_approval_service_set_paused(TRUE)` then `FALSE`, and evaluate a distinct request with the same tuple/flow/size. It returns **ALLOW**, not ASK. This used a disposable permission store; no crypto or developer-keychain access was needed.
- **Impact:** pausing is not the requested consent-invalidating security boundary. An interrupted send or a later same-flow call can resume required-confirmation signing without a new review, until count/expiry exhaustion.
- **Recommendation:** clear all ephemeral flow consent on transition to paused, update the expiry/revision fence, and retain the existing cancellation of queued/in-flight work. Test fresh post-resume requests, not only old cancelled requests.

### F2 — High, platform-conditional · Confirmed in source: the new consent API accepts the inherited UID-only trust fallback

- **Location:** `nips/nip55l/src/glib/signer_service_g.c:135-150,243-253,286-291`; `nips/nip55l/src/glib/signer_caller.c:363-375,393-401,562-573`; `nips/nip55l/src/glib/signer_approval_service.c:332-346,1177-1194`; `apps/grotto/src/ui/approval_dialog.c:524-535`.
- On a bus without caller PIDs, the compatibility path marks same-UID callers `unattested`, accepts their claimed principal, and considers **any** such caller an approver. `ApproveFlowRequest` uses that helper unchanged. The service checks only that a principal exists, not that it is verified; the UI uses `rememberable` rather than `verified` to offer flow choices.
- Therefore, on that path, an attacker-controlled same-user app can answer a pending flow-bearing review itself, without a human decision, and can claim another app's principal to consume its flow consent. For plain encryption / Groundhog's empty claimed name this can be the shared `claimed:` principal. Flow ID secrecy is not a defense: the same approver fallback permits approval-metadata access.
- **Qualification:** this is an **inherited, explicitly documented** limitation (`docs/dbus-interface.md:265-271`), not a newly introduced PID-verified Linux caller-spoofing bug. The new required-confirmation exception nevertheless does not meet an unconditional “verified principal / explicit user decision” claim on this supported compatibility path. No cross-app bypass was found for genuinely different verified principals.
- **Recommendation:** disable minting **and consumption** of this new flow-consent exception for unattested/claimed callers, and keep ordinary per-request review behavior; do not imply that hiding the checkboxes alone fixes the daemon boundary. The existing broader compatibility policy is not otherwise reviewed here.

### F3 — Medium · Confirmed: persistent-store errors prevent ephemeral revocation

- **Location:** `nips/nip55l/src/glib/signer_permissions.c:582-592`; `nips/nip55l/src/glib/signer_approval_service.c:1218-1235`; client-wide revoke `apps/grotto/daemon/grotto_control.c:680-689`.
- `signer_permissions_clear()` reloads persistent records and, if needed, commits their removal **before** clearing in-memory flows. Reload failure or persistent-write failure returns with flow consent intact. `RevokeClient` cancels current requests first, but removing the client record / changing the policy revision does not itself remove flows.
- **Local reproduction:** mint a three-slot seal flow, replace the disposable permissions file's version with an unsupported value, invoke `signer_approval_service_revoke_grant()`, restore the original file, then evaluate a new same-flow request. Revoke returns failure; after repair the old consent returns **ALLOW** without another review. A failed persistent commit follows the same early-return shape.
- **Qualification:** this is **not** a falsely successful revoke. The operation reports an error, and evaluation fails closed while the store remains unreadable. The problem is residual authority reviving after repair (or remaining immediately usable after a write-only failure).
- **Recommendation:** invalidate matching ephemeral consent and fence its automatic admissions independently of durable-store success; continue reporting any persistent revocation failure honestly. Cover both read and write failure, plus `RevokeClient`, not just direct evaluator clearing.

### F4 — Medium · Plausible user-intent attack: same-principal flows are a shared budget, not authenticated sends

- **Location:** `nips/nip55l/src/glib/signer_permissions.c:31-37,412-424,448-477,558-578`; UI promise `apps/grotto/src/ui/approval_dialog.c:536-540` and `apps/grotto/data/ui/approval-dialog.blp:64-65`.
- **Confirmed mechanics:** lookup binds the exact principal/identity/transport/operation/kind/flow ID and size, but not the caller connection/process instance, rumor, destination set, encryption result, or `purpose`. A kind-13 request with the matching tuple can use an unused slot regardless of which logical send produced it. A malicious or compromised instance of the **same principal**, knowing or choosing an in-progress flow ID and size, can submit its unrelated seal first and consume that budget. It cannot borrow a different verified principal's flow, change the allowed kind, or increase the budget this way.
- Groundhog generates one random UUID per envelope build (`gnome/groundhog/src/app/gh-nip17-envelope.c:195-200,250-257`), so accidental collisions in the honest implementation are not a credible finding. Deliberate reuse by the caller is possible; this is not an inter-app collision attack on the verified-principal path.
- **First-seen/lifetime answer:** there is **no first-seen window** or completed-flow tombstone. The monotonic deadline starts when consent is minted (`signer_permissions.c:448-455`), not when the first flow-bearing request arrives. An active flow cannot be reset, enlarged, or extended by another consent call (`:560-563`), and use never refreshes it. After expiry it is pruned (`:436-446`) and the same ID may be minted again **only through another explicit approver decision**. Reuse alone does not silently extend ten-minute consent; it can spend leftover slots on another send within the original window.
- **Risk / recommendation:** the source establishes a bounded same-principal capability, not cryptographic proof of “only this send.” Treat unrelated-send piggyback as plausible when that stronger promise matters. Make the contract/copy explicit, add a deliberate same-principal interleaving test, and obtain a product decision before inventing a daemon-verifiable send binding or a first-seen rule. Do not describe this as an unbounded lifetime bypass.

| Decision is pinned to a flow-bearing review | `signer_service_g.c:286-291` checks the approver; `signer_approval_service.c:1177-1194` requires an announced pending request carrying a principal, flow ID, positive size, room-send purpose, encrypt or exact seal operation, live request deadline, and unpaused service. | No automatic cross-scope use | `signer_permissions.c:90-101,412-424,458-477`: length-delimited hashed principal/identity/op/kind plus transport and exact flow ID; size must also match. No-flow requests cannot use the exception. A D-Bus connection ID is not part of the binding, intentionally allowing Groundhog's per-call connections. |
| Exact count | `signer_permissions.c:469-477` counts daemon request IDs, admits at most `size` per operation/kind, and reuses an existing request reservation on policy recheck. Count exhaustion or size mismatch returns ASK, not ALLOW. `signer_approval_service.c:880-895` disables request joining whenever either request has a nonzero size, preventing several calls from hiding behind one slot. Cancelled/failed reservations are not refunded: conservative, not a budget increase. An additional **individually approved** excess request is a new decision, not automatic consent. |

Size 1024 is legal and honestly caller-declared; it is not checked against an independently known room membership. |

Serialization/listing/migration visit `records` only (`:142-156,258-280,506-515,641-650`); there is no flow-to-row conversion. Ordinary Remember rows still cannot bypass a required kind (`:391-396`). ## “Approve selected once” and G07 controller interplay

No authorization of future unseen requests was found in this path.

- Rows are rendered with operation, kind, and peer, start unchecked, and the handler extracts only checked row IDs (`apps/grotto/src/ui/approval_dialog.c:168-194,408-435`). The controller also checks membership in the dialog's **frozen** batch, READY state, and matching group before issuing individual `ApproveRequest(TRUE, FALSE, 0)` decisions (`apps/grotto/src/approval-controller.c:882-894`). It never calls the flow-minting method for this button.
- Grouping is exactly principal + resolved identity + transport + flow ID, with a nonempty principal (`approval-controller.c:814-821`). Explicit-flow rows are batched; flow-less concurrent requests receive presentation/stepper grouping only (`:1022-1036`). Different operations are allowed in the same presentation because each displayed row gets its own decision.
- New arrivals update navigation **without mutating the checked-ID set** (`:907-947`). Moving the stepper opens a fresh review, rebuilding its batch. Single/flow decisions use G07's next-group progression (`:823-865`); selected-once decisions complete independently and leave remaining requests pending (`:875-894`), rather than silently selecting/approving the next item.
- Each decision re-fetches metadata and compares pinned scope, including the new flow fields, before submission (`:268-278,714-772`); owner-generation/deadline guards remain in that controller path. Batch discovery has no debounce or waiting timer: the current model is rendered immediately (`:1022-1046`). Notification coalescing is not batch discovery.
- Relevant tests include visible-ID membership and checkbox extraction (`apps/grotto/tests/test-approval-dialog.c:264-291`) and injected unseen same-flow IDs / arrival-with-selection (`apps/grotto/tests/test-approval-integration.c:351-387`). These GUI paths were source-reviewed, **not executed by the headless macOS integration run**.

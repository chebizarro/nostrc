# Grotto W2 panels scaffold — focused architecture/boundary review

## Scope and verdict

Reviewed local `grotto/w2-panels-scaffold` at **`9115d56b751c5945f4b14ae116ff7ea1e426ba6e`** against local `master` **`e383c1bac62d6f8886589625d14c780e58603bff`** (also their merge base). Scope: design §b.4, §c.1–c.3, §c.6 and Q1; the new library, host dependency wiring, component version and selector inventory only. This document is the only repository-file change made for the review. No product fixes, commits, pushes or merges.

**Verdict:** the present library/adapter separation is sensible, and the level-1 host actually mounts under xvfb. However, the advertised no-secrets gate is demonstrably bypassable, the fake is not a faithful command double, and Grotto's new runtime library has an uncovered package boundary. Do not equate the current green ordinary tests with enforcement of every §c.3 rule or leak-clean teardown.

“Confirmed” below means source-confirmed, or executed where explicitly stated. “Plausible” labels consequences not reproduced end-to-end; it does not mean a proven exploit or leak. Severity concerns this scaffold, not a repository-wide security assessment.

## Findings, ranked

### 1. P1 — `no-secrets` accepts both an extra credential field and an actual forbidden RPC

**Confirmed by compiled, isolated mutation checks.** Owning evidence: `gnome/grotto-panels/tests/test-boundaries.py:11–35`, especially the incomplete field extraction at **19–22** and source/symbol matching at **11–15, 25–35**.

The schema assertion recognizes only four exact C type spellings, compares a set of the fields it happened to recognize, and rejects only four opaque type names. Adding `const gchar *pairing_token;` to `GrottoPanelsMetadata` leaves that extracted set unchanged. I built this modified library in a temporary copy and the unmodified boundary test printed PASS. This is directly contrary to the requested public-metadata-only contract, not merely a theoretical parser limitation.

Separately, I added an exported function to a temporary copy of the compiled library source containing:

```c
g_dbus_connection_call(bus, "org.nostr.Signer", "/org/nostr/signer/grotto",
  "org.nostr.Grotto.Control1", "Decide" "Request", NULL, NULL,
  G_DBUS_CALL_FLAGS_NONE, -1, NULL, NULL, NULL);
```

The rebuilt ELF contained the `DecideRequest` string, imported `g_dbus_connection_call` and exported the probe function. The same test still printed PASS: the source regex misses adjacent C string literals, `nm` does not inspect RPC string constants, and generic GIO dispatch is allowed. **The probe function was never called; no approval RPC was sent.** Both mutations lived only inside disposable containers, not this worktree.

The current production sources do not contain these mutations, and I found no actual secret-returning operation in the present library. The finding is that the promised architectural regression gate fails its central purpose. Its final message also overstates semantic “no policy” enforcement. A focused correction should validate the complete declared schema and constrain compiled library dispatch/import boundaries, with negative mutation tests, rather than extend the spelling blacklist. New source subdirectories are another unexamined surface of the immediate `src/*.c` glob at line 14.

### 2. P2 — the new shared-library dependency does not reach Grotto's native package closure

**Confirmed static wiring omission; package-build/startup failure is plausible, not executed.** `apps/grotto/CMakeLists.txt:236–237` adds the production adapter and links `GrottoPanels::Panels`; `gnome/grotto-panels/CMakeLists.txt:14–17, 31–35` makes this an installed shared library in `${CMAKE_INSTALL_LIBDIR}`. But `apps/grotto/packaging/debian/grotto.install:1–16` includes only `usr/lib/grotto/*`, not the new top-level `usr/lib/libgrotto-panels-0.so*`. Its packaging route explicitly sets `CMAKE_INSTALL_LIBDIR=lib` and installs the Grotto subtree (`packaging/debian/rules:11–25`).

The existing private-library closure handles JSON and `nostr_gobject`, not panels (`apps/grotto/CMakeLists.txt:495–511`). Debian's `${shlibs:Depends}` (`packaging/debian/control:36–39`) is not a substitute for either packaging the new library or defining its provider/runtime dependency. Thus the source now installs a runtime DSO outside the package's listed payload, with no corresponding provider introduced by this branch. Depending on packaging-stage handling this can surface as an unclaimed install/dependency error or an unavailable library for the GUI.

This is the specific §c.1 runtime-package dependency gap caused by the new link, not a request for a packaging-platform matrix. I did not build a Debian package or claim an observed deployed startup failure. Meson's new `dependency('grotto-panels-0', version: '>= 0.1.0')` also requires the library to be installed first; its README documents that prerequisite, but it does not resolve the Debian payload gap.

### 3. P2 — the fake is configurable at the guard layer, but every dispatched command succeeds

**Confirmed static contract gap.** `gnome/grotto-panels/tests/fake-service.c:18–23` discards both command and arguments and immediately returns TRUE. Availability, capabilities and list updates are useful controls (`:44–59`), and GTask provides cancellation semantics, so this is not an entirely inert stub. However, once the public wrapper admits a valid, available, permitted invocation (`src/grotto-panels-service.c:81–93`), the fake cannot produce a daemon rejection/conflict, delay completion, observe the requested operation, or model its effect.

`tests/test-smoke-host.c:117–145` tests wrapper rejection and one successful pause, not post-dispatch failure. The real adapter can propagate RPC errors and cancel an old-owner completion (`apps/grotto/src/grotto-panels-control1-service.c:175–185`); the fake cannot exercise those paths. Consequently a panel which ignores a daemon-side refusal or mishandles an in-flight detach can pass this fake smoke test. A configurable recorded invocation/result and controlled completion would suffice; the fake need not reimplement signer policy.

## Boundaries that are sound in the current implementation

- **Public read surface and no panel policy:** models contain immutable, copied display fields (`include/grotto-panels-0/grotto-panels.h:18–40`; `src/grotto-panels-service.c:24–35`). The current adapter explicitly projects named fields and drops unknown dictionary keys (`apps/grotto/src/grotto-panels-control1-service.c:48–90`); it does not pass the daemon dictionary, request preview/content, secret key, mnemonic or pairing offer through the interface. Command results are boolean, not arbitrary RPC payloads (`grotto-panels.h:79–84`; adapter `:175–185`). The row helper displays label/reason and disables markup, with no permission interpretation (`src/grotto-panel.c:101–110`). This is a source observation, not a claim that the static test proves all future changes safe.
- **Authority split is explicit, not implemented in GTK:** read models are separate from commands; pause/resume are distinct; access classification marks label as manager, pause as session, everything else as approver (`grotto-panels.h:50–71`; `grotto-panels-service.c:38–47`). The adapter uses a closed RPC table and ignores today's coarse capability map, defaulting command capabilities to false until a caller-specific map exists (adapter `:21–29, 98–109`). No manager authorization is granted here; the existing daemon still checks its caller (`apps/grotto/daemon/grotto_control.c:658–669`). W6's reads/labels support can therefore be additive without making Settings an approver. Host callbacks keep review, backup, onboarding, removal and replacement outside the shared library (`grotto-panels.h:99–108`).
- **Important scope discrepancy:** the review brief says manager “labels/tiers,” whereas design §c.4 explicitly excludes `SetClientTrust` from the manager role (`docs/designs/grotto-settings-style-ux-2026-11-03.md:339–347`). The code follows the narrower design: tier/trust changes are approver-only. Manager tier editing is **not** implemented by this classification. Clarification was requested; absent an answer, this review does not silently treat either expanded tier authority or removal of the hand-off as approved.
- **Dependency direction:** the production DSO builds only two library sources and links GTK/libadwaita's GLib/GIO closure (`CMakeLists.txt:10–27`; `meson.build:4–9, 19–27`). No `nostr-gobject`/NIP-55L types or executable symbols appear in its public API. The Grotto-owned GIO adapter is compiled into the host, not the DSO (`apps/grotto/CMakeLists.txt:236–237`; `apps/grotto/meson.build:283`). This fits the W2 Grotto-owned adapter boundary; W3's metadata composite and W6's Settings adapter remain future work. The MIT sources/license do not copy the GPL bridge implementation. No AGENTS.md dependency or change was introduced.
- **Injection shape:** the bridge reference deliberately has a global copied vtable, optional operations and GIO async/error conventions (`nostr-gobject/include/nostr-gobject-1.0/gnostr-signer-bridge.h:3–12, 32–74`). Per-instance GInterface injection is the intentional §c.2 refinement, not a mismatch. The panel retains the service, copies callbacks, owns a view cancellable and disconnects its two service signals on detach/dispose (`src/grotto-panel.c:21–39, 51–64, 74–85`). Absent service and unsupported/denied operations fail closed through asynchronous GErrors (`grotto-panels-service.c:74–108`).

## Build, selector and version assessment

- **Build-system agreement:** CMake and standalone Meson both build the same hidden-visibility shared ABI, public headers, version 0.1.0, SONAME major 0, and `grotto-panels-0.pc`; GTK 4.14/adwaita 1.5 min/max API pins agree (`CMakeLists.txt:3–27, 31–45`; `meson.build:2–27`; `grotto-panels-0.pc.in:6–11`). The test-only private-bus helper is not a production dependency. CMake's extra helper selftest accounts for its four tests versus Meson's three. CMake exports `GrottoPanels::Panels`; Meson supplies pkg-config. Cross-build-system CMake-config consumption of a Meson-only installation was not tested.
- **Conventions/version:** `declare_component_version` is used with a sanitized generated public header as the repository helper supports (`cmake/VersionHelpers.cmake:12–55`), consistent in principle with `nostr-gtk/CMakeLists.txt:18–24` and `nostr-gobject/CMakeLists.txt:16–22`. `VERSION_MANIFEST.md:33` correctly declares the new **0.1.0**, lists both authoritative project versions and generated surfaces, and leaves release/tag unpublished. Installed CMake pkg-config returned 0.1.0. No version-source mismatch found. The implementation bead records no bumps for Grotto/Settings/nip55l/nostr-gtk/nostr-gobject because this is unactivated scaffold with no changed user functionality or daemon authority; the new runtime-package obligation still needs resolution (finding 2). This report is documentation-only and needs no component bump.
- **Selector entries:** new component/check/profile and three path rules are focused (`tests/selection/inventory.json:23–37, 21978–21982, 24325–24342, 29237–29252`); both host nodes depend on the component (`:22227–22233, 22320–22326`), and the canonical Control1 XML also impacts its check (`:28834–28842`). The check selects the three component tests and builds their executables; missing Linux display/bus runners fail configure, not silently skip. The NIP-55L fixture addition correctly retains this downstream adapter consumer (`tests/selection/fixtures/nip55l_affected.json:442`). No unrelated dependency was added to the library node.
- **Actual affected plans:** exact-base/head unfiltered `--explain` selects `grotto.panels` in both `grotto.panels.linux` and `grotto.linux`. It conservatively broadens to **430 checks / 21 lanes**, explaining inventory ownership/policy changes and the pre-existing Settings profile coverage gap. The explicitly partial `--profile grotto.panels.linux --explain` selects only `grotto.panels`. Thus inclusion and scoped omission are demonstrated; neither plan is test execution, unrestricted affected-only coverage, or hosted acceptance. No selector regression found within this scope.

## 1. Scope + what this proves

The acceptance question is: **does the real GDM PAM stack, using the
Debian `pam-auth-update` profile that packaging ships, authenticate a
seeded nostr account via the broker, deny wrong proofs, and leave
ordinary local users unaffected?**

The definitive automatable proof is `pamtester` against the exact
service file GDM invokes (`/etc/pam.d/gdm-password`). GDM's greeter
uses libpam.so which is the same library pamtester links, and
`gdm-password` `@include`s `common-auth` (which is the file
`pam-auth-update` rewrites when the `nostr` profile is enabled).
Passing pamtester = passing GDM at the credential + PAM-verdict layer.

Live-driving the greeter over SSH cannot be done reliably; the manual
click-through procedure is documented in §6 for operator verification.
Whether the operator clicks or pamtester runs, the underlying PAM
service, module, socket, broker, NSS projection and vault are identical.

## 3. Seed n_gdm, start broker, wire NSS + PAM

```sh
sudo mkdir -p /var/lib/nostr-auth && sudo chmod 0700 /var/lib/nostr-auth
sudo /usr/sbin/nostr-homed-seed /var/lib/nostr-auth n_gdm "correct horse battery staple"
# -> seeded n_gdm (uid=200000) pubkey=79be667e...b16f81798 in /var/lib/nostr-auth

sudo systemctl daemon-reload
sudo systemctl start nostr-authd.service
# journal: nostr-authd: auth listening on /run/nostr-auth/auth.sock, user on /run/nostr-auth/user.sock

# Sockets (auth.sock is 0600 root-only, user.sock is 0666 for unprivileged callers):
srw------- root root /run/nostr-auth/auth.sock
srw-rw-rw- root root /run/nostr-auth/user.sock

# Wire NSS
sudo chmod 0644 /etc/nss_nostr.conf /var/lib/nostr-auth/nss.db
sudo chmod 0755 /var/lib/nostr-auth
sudo sed -i '/^passwd:/ { /nostr/! s/$/ nostr/ }' /etc/nsswitch.conf
sudo sed -i '/^group:/  { /nostr/! s/$/ nostr/ }' /etc/nsswitch.conf
# Result: passwd: files systemd sss nostr

# Enable the pam-auth-update profile (nostr is stacked above pam_unix in Primary)
sudo pam-auth-update --package --enable nostr
```

Rendered `/etc/pam.d/common-auth` after enablement (verbatim):

    auth  [success=3 new_authtok_reqd=ok user_unknown=ignore authinfo_unavail=ignore default=die]  pam_nostr.so socket=/run/nostr-auth/auth.sock
    auth  [success=2 default=ignore]  pam_unix.so nullok try_first_pass
    auth  [success=1 default=ignore]  pam_sss.so use_first_pass
    auth  requisite                   pam_deny.so
    auth  required                    pam_permit.so
    auth  optional                    pam_cap.so

Rendered `/etc/pam.d/common-account`:

    account  [success=2 user_unknown=ignore authinfo_unavail=ignore default=die]  pam_nostr.so socket=/run/nostr-auth/auth.sock
    account  [success=1 new_authtok_reqd=done default=ignore]                     pam_unix.so
    account  requisite                                                            pam_deny.so
    account  required                                                             pam_permit.so
    account  sufficient                                                           pam_localuser.so
    account  [default=bad success=ok user_unknown=ignore]                         pam_sss.so

The `success=end` in the shipped profile is translated by pam-auth-update
into the correct positional jump (`success=3`) that skips over pam_unix,
pam_sss and pam_deny to land on pam_permit. `user_unknown=ignore` and
`authinfo_unavail=ignore` propagate exactly. `default=die` propagates:
a known nostr account that fails its proof is denied without any
downgrade path to Unix passwords. The strict-deny posture from
nostrc-o1ho is preserved end-to-end.

Prerequisite for the co-existence proofs: a stock local Unix user was
provisioned before the test.

```sh
sudo useradd -m -s /bin/bash b6local
echo 'b6local:localpass-b6' | sudo chpasswd
```

## 4. Definitive pamtester proofs against the REAL gdm-password stack

Every command below invokes `pamtester` against the exact service file
GDM's greeter uses — `/etc/pam.d/gdm-password`, which `@include`s
`common-auth` (the file pam-auth-update rewrites). The credential path
is identical to a real greeter login.

| # | Service        | User      | Input                            | Expected      | Result | pam_nostr verdict (auth.log) |
|---|----------------|-----------|----------------------------------|---------------|--------|-------------------------------|
| 1 | gdm-password   | n_gdm     | `correct horse battery staple`   | PAM_SUCCESS   | RC=0   | `authenticate n_gdm (local) -> ok` |
| 2 | gdm-password   | n_gdm     | wrong passphrase ×3              | AUTH_ERR      | RC=1   | `authenticate n_gdm (local) -> invalid_proof` ×2 then protocol_error |
| 3 | login          | n_gdm     | `correct horse battery staple`   | PAM_SUCCESS   | RC=0   | `authenticate n_gdm (local) -> ok` |
| 4 | login          | n_gdm     | wrong passphrase ×3              | PAM_MAXTRIES  | RC=1   | `authenticate n_gdm (local) -> invalid_proof` ×3 |
| 5 | gdm-password   | b6local   | `localpass-b6` (local Unix pass) | PAM_SUCCESS   | RC=0   | `begin_login b6local -> unknown_account` (falls through to pam_unix, succeeds) |
| 6 | gdm-password   | b6local   | wrong local password ×3          | AUTH_ERR      | RC=1   | (unknown_account → pam_unix denies) |
| 7 | gdm-password   | nh_ghost  | any input                        | AUTH_ERR      | RC=1   | `begin_login nh_ghost -> unknown_account`; pam_unix: user unknown |
| 8 | gdm-password   | n_gdm     | acct_mgmt                        | PAM_SUCCESS   | RC=0   | account chain returned success |
| 9 | gdm-password   | b6local   | acct_mgmt                        | PAM_SUCCESS   | RC=0   | pam_localuser sufficient |

Verbatim transcript excerpts (from `auth.log` at 2026-09-22T08:03–08:04):

    pam_nostr(gdm-password:auth): nostr: authenticate n_gdm (local) -> ok
    pam_nostr(gdm-password:auth): nostr: authenticate n_gdm (local) -> invalid_proof
    pam_nostr(login:auth):        nostr: authenticate n_gdm (local) -> ok
    pam_nostr(login:auth):        nostr: authenticate n_gdm (local) -> invalid_proof (repeated 2× → PAM_MAXTRIES)
    pam_nostr(gdm-password:auth): nostr: begin_login b6local -> unknown_account
    pam_nostr(gdm-password:auth): nostr: begin_login nh_ghost -> unknown_account
    pam_unix(gdm-password:auth):  check pass; user unknown          # for nh_ghost after fall-through
    pam_unix(gdm-password:auth):  authentication failure ... user=b6local   # only in the wrong-password variant

### Interpretation

- **Nostr success is authoritative** (rows 1, 3): the broker verified a
  fresh proof against the enrolled pubkey and `default=die` is never
  reached; `success=3` jumps past pam_unix/sss/deny to pam_permit.
- **Nostr failure is fatal**, without downgrade (rows 2, 4): a known
  nostr account with a wrong proof returns `PAM_AUTH_ERR` /
  `PAM_MAXTRIES` and `default=die` refuses the login. `pam_unix` is
  *never* invoked for the nostr account — confirmed by absence of any
  `pam_unix(...) authentication failure ... user=n_gdm` line in auth.log
  for the wrong-passphrase runs, in contrast to the b6local case where
  pam_unix does log the failure.
- **Unknown-to-broker accounts fall through** (rows 5, 6, 7): the
  broker returns `NH_AUTH_RESULT_UNKNOWN_ACCOUNT`, `user_unknown=ignore`
  lets pam_unix take over; b6local logs in normally with the local
  password, an unknown ghost user is rejected by pam_unix. **Local
  login is not bricked by the nostr stack.**
- **Broker outage safety** (documented, not induced in this run): the
  profile maps `authinfo_unavail=ignore`, so if `nostr-authd` were
  stopped, the same "fall through to pam_unix" behaviour would apply
  for every user; a nostr-only account would then simply fail at
  pam_unix. This is the intended fail-safe (nostrc-o1ho).

### NSS resolution

    $ getent passwd n_gdm
    n_gdm:x:200000:200000:Nostr User:/home/n_gdm:/bin/bash
    $ getent passwd nh_nonexistent          # empty (NOTFOUND, not error) ✓
    $ getent passwd debugger                # local user still visible ✓
    $ getent passwd b6local                 # local user still visible ✓

Note on the pre-existing artifact `n_smbd7g` in `/etc/passwd` from an
earlier Track 3 (D7 SMB) run: because `files` precedes `nostr` in the
nsswitch order, `getent passwd 200000` returns `n_smbd7g` rather than
`n_gdm` for the reverse-UID lookup. Forward lookups (`getent passwd
n_gdm`) hit the nostr module correctly and authenticate. This is a
harmless collision in the lab; production deployments would not
pre-seed `n_*` entries into `/etc/passwd`.

## 5. GDM greeter — automated attempt + manual procedure

The x86_64 GNOME desktop's greeter runs on `tty1` and is Wayland-based.
Live-driving it over SSH cannot be done reliably (no accessible
keyboard/pointer injection into the login screen — `ydotool` requires
a running compositor user session, and GDM's greeter uses an isolated
`gdm` user Wayland instance). What is confirmed:

- `systemctl is-active gdm` → `active` throughout the entire run
  (before, during, after enablement + teardown).
- `/etc/pam.d/gdm-password` is unmodified from the shipped Ubuntu
  template; the `nostr` stacking is entirely inside `common-auth`
  (managed by `pam-auth-update`). The greeter therefore invokes the
  same `common-auth` block that `pamtester -v gdm-password …`
  invoked above.

### Manual click-through (for operator, from a physical console)

1. Ensure the profile is enabled and the broker is running:
   `sudo pam-auth-update --package --enable nostr && sudo systemctl start nostr-authd`.
2. Seed the account (see §3) — passphrase = `correct horse battery staple`.
3. From the GDM greeter (Ctrl+Alt+F1 to reach tty1 if the greeter is
   not already foreground): click *Not listed?*, type `n_gdm`, press
   Enter, then type the passphrase in the password field and press
   Enter.
4. Expected: on the correct passphrase, GDM proceeds into the seeded
   `/home/n_gdm` GNOME session. On a wrong passphrase, GDM shows the
   red "Sorry, that didn't work" banner and refuses without any
   downgrade path (strict-deny). This is the same outcome pamtester
   proved above; if pamtester passes, this step passes.
5. After test, log out (or `Ctrl+Alt+F1` back to the greeter), then
   run the teardown in §7.

### NIP-46 provider at the greeter (deferred, not blocking)

## 6. Observations + follow-ups

### 6.1 pam-auth-update parser warnings on our profile (cosmetic)

Every `pam-auth-update` invocation on `/usr/share/pam-configs/nostr`
prints warnings of the form:

    Use of uninitialized value $fieldname in hash element at /usr/sbin/pam-auth-update line 734, <PROFILE> line 41.

for the lines in the comment header that contain a colon inside a
bulleted list (lines 38–42 in the profile:
`# Prerequisites (see docs/INSTALLED_LOGIN.md):`,
`#   - nostr-authd running with auth.sock at /run/nostr-auth/auth.sock`,
etc.). Debian's `pam-auth-update` parser appears to treat a comment
line that contains a `:` inside an already-started record as a
malformed field. The profile is applied correctly despite the warnings
(verified: enable → rendered common-auth is correct; remove → rendered
common-auth is stock). Filed as a follow-up cleanup — should be a
one-line reflow of the comment block that avoids `:` inside bulleted
comments after the record header, or moves the prose to a separate
`README.md`.

### 6.2 Retry budget mapping

The `login` service exhibits `PAM_MAXTRIES` (row 4) because
`pamtester` retried three times and the retry budget in
`pam_nostr` is `<= 3`. `gdm-password` also honours the budget — the
wrong-passphrase test that uses the graphical prompt would get one
retry per greeter attempt. This matches the B5 acceptance ("max three
bad choices").

### 6.3 Coexistence

`b6local` authenticated cleanly through the same `gdm-password`
service with `pam_nostr` above it. No local user was locked out,
which is the specific "no lockout" requirement stated in the prompt.
`debugger` (uid 1000, sudoer) remained SSH-reachable throughout.

## 8. What this closes / what it does not

**Closes for B6 (nostrc-zcll.7), for the local-vault provider on
Ubuntu 24.04 amd64:**

- Real `gdm-password` PAM stack authenticates the seeded nostr account
  via the broker (correct passphrase → PAM_SUCCESS).
- Real `gdm-password` PAM stack refuses the account with a wrong
  passphrase (`default=die`, no Unix downgrade).
- Real `login` PAM stack behaves identically.
- NSS resolves the account through the installed `libnss_nostr.so.2`.
- Ordinary local Unix users still log in through the same
  `gdm-password` service after the profile is enabled (co-existence /
  no lockout).
- Ordinary local Unix users still log in after the profile is removed
  (stock restore is clean).
- Broker unit + sockets have the documented modes (auth.sock 0600,
  user.sock 0666).

**Does not close (explicitly deferred, filed for follow-up):**

- Live greeter click-through (documented manual procedure; identical
  PAM chain as pamtester — operator verification).
- NIP-46-at-greeter (needs a fresh operator bunker grant; documented
  in §5, tracked under nostrc-ot2c.7).
- 100-cycle automation, lock/unlock, suspend/resume, greeter restart,
  reboot fault matrix (these belong to the full B6 acceptance battery
  and are not part of this "prove the credential path" gate).

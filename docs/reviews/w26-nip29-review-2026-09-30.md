**Reviewer:** independent peer review\

## Verdict: APPROVE

## Summary

The fix correctly addresses the root cause: when NIP-42 AUTH fails at
subscription time (signer unavailable, bunker not ready, or relay refusing),
the relay sends CLOSED with `auth-required:` and rooms enter AUTH_REQUIRED
permanently. Without a recovery path, the subscription is never rebuilt —
only local outbox echo inserts the user's own messages, so the room looks
like a monologue.

The fix adds an `on_auth_state_changed` signal handler to GhNip29Service,
following the same pattern already used by GhDmInbox and GhOutbox. When
GhAuthPolicy emits `account-state-changed` for a relay URL, the handler
checks whether any room on that relay is stuck in AUTH_REQUIRED and, if so,
calls `relay_resubscribe` — which cancels/unrefs the old scope first.

### Detailed review notes

**Signal handler correctness:**
- `g_signal_connect_swapped` correctly swaps the instance/data arguments so
  the handler receives `(GhNip29Service *self, const gchar *url)` matching
  the `account-state-changed` signal's `(GhAuthPolicy *, const gchar *)`
  signature.
- The handler is guarded by `running(self)` (false when generation is 0 or
  offline), `!relay` (URL not tracked), `!relay->scope` (no subscription),
  and the AUTH_REQUIRED room check (avoids unnecessary resubscription).

**No subscription leak or duplicate:**
- `relay_resubscribe` calls `relay_close` which cancels and unrefs the old
  scope before creating a new one. The old scope's callbacks check
  `relay->scope != scope` and bail out.
- On account switch: `update_activity` closes all relays and calls
  `sync_all`, so the handler's `running(self)` check prevents interference.
- On reconnect: the handler only triggers on auth state changes, not
  connection state changes; those are handled by `on_scope_update`
  (DISCONNECTED notice).

**Dispose safety:**
- `policy_handler` is disconnected in `gh_nip29_service_dispose` before
  relay cleanup (`g_hash_table_remove_all(self->relays)`), matching the
  pattern of `accounts_handler` and `network_handler`.

**Reply helper (`nip29_member_reply`):**
- Correct NIP-29/NIP-C7 tag structure: `h` (group), `q` (quoted root),
  `e` (reply marker), `p` (reply-to author), `previous` (ordering).
- All fields NULL-guarded. Reply kind is 9, matching the spec.

**Reply rendering:**
- Replies from other members are received and displayed as flat messages in
  the conversation. Threading/reply-rendering is not implemented in the
  NIP-29 service (no reply-to parent tracking). The brief notes this should
  be filed as a separate bead (nostrc-zjkv).

**Test quality:**
- `test_reply_events_and_multi_member`: verifies Bob's message and Carol's
  tagged reply both appear, from different members, signed (not local echo),
  live messages arrive, kinds 10/11/12 are received, all survive
  restart+backfill, and live messages work after restart. Passes on master
  (the filter was never broken).
- `test_auth_recovery_on_state_change`: verifies the stuck-in-AUTH_REQUIRED
  scenario end-to-end — private group, AUTH required, AUTH refused after
  restart, rooms stuck, signal emission triggers recovery, missed messages
  arrive, live messages work post-recovery, recovered messages verified as
  non-self and signed. **Fails on master** (10s timeout at
  `wait_read(stuck, GH_NIP29_READ_LIVE)`) — confirmed by revert test.

**Version bump:**
- No separate bump; PATCH-level fix folded into unreleased Groundhog 0.12.0.
  VERSION_MANIFEST entry is thorough and correct.

**Log level change:**
- `g_debug` → `g_info` for "Groundhog will not sign in to a group relay" is
  appropriate: this message is diagnostic for the exact scenario the bug
  describes, and `g_info` makes it visible in normal (non-debug) logs.

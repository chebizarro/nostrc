## Findings, ranked

### F1 — S2, confirmed/executed and static — New offline reasons copy credential-bearing relay URLs into status and normal logs

**Where:** `apps/grotto/src/bunker_service.c:555-557`, passed unredacted to `set_state()` at `:108-113`; admitted relay inputs at `apps/grotto/src/pairing_uri.c:12-24` and `apps/grotto/src/bunker_service.c:683-695`. Control1 exposes the reason at `apps/grotto/daemon/grotto_control.c:185-187`; the new adapter/display wiring is `apps/grotto/src/grotto-panels-control1-service.c:189-190` and `gnome/grotto-panels/src/grotto-remote-panel.c:132`.

The new reason interpolates the whole relay URL. Userinfo and fragments are rejected, but the host accepts query parameters, and nip55l normalization preserves them (`nips/nip55l/src/core/signer_ops.c:1382-1403`). There is no credential redaction before the reason becomes a normal `g_message` journal entry or a `bunker_error` value. Turning off markup correctly prevents markup interpretation; it does not sanitize sensitive content.

**Failure scenario:** an authenticated relay URL supplied through the host configuration or a confirmed client URI uses a query credential, then goes offline. A diagnostic linked against the unchanged production service/transport objects started `ws://127.0.0.1:1/?password=review-credential-marker` in an isolated profile. The real connection-state callback produced both `BUNKER_STATE state=OFFLINE error=Could not connect to ...?password=review-credential-marker (OFFLINE)` and the same service error value. The marker is disposable test text, not an operator credential. Control1 propagation is source-confirmed; this was not a live GUI credential-disclosure demonstration. In fact the panel rejects this query URL (F2), so it must not be claimed that this exact URL rendered successfully in the panel.

Use a bounded, explicitly public relay identifier in status/errors, or reject unsupported credential-bearing URL forms consistently before persistence/contact. Do not rely on the panels' lexical secret-marker check as a redactor. Lower-level pool logs also printed this diagnostic URL; that existing logging behavior is not attributed to this diff. This finding concerns the newly added, independently unsanitized status reason, not account-key leakage or a claim that all URL logging originated here.

### F2 — S2, confirmed/executed and static — The repaired relay editor still validates a different URL language from the host

**Where:** `gnome/grotto-panels/src/grotto-panels-validation.c:53-62`; new entry validation at `gnome/grotto-panels/src/grotto-remote-panel.c:63-70`; host rules at `apps/grotto/src/pairing_uri.c:12-24` and `apps/grotto/daemon/grotto_control.c:625-632`.

The shared panel validator accepts `wss://example.onion/`, while pairing/service validation rejects it. Conversely, the host accepts relay queries while the panel rejects every query. An executed diagnostic using the actual validators returned `panel=1, host=0` for the onion URL and `panel=0, host=1` for the query URL. Ordinary `wss://`, loopback `ws://`, rejection of non-loopback `ws://`, and rejection of userinfo agreed.

**Failure scenario:** Add Relay accepts an onion-shaped WSS candidate locally, dispatches it, then the host refuses it and the panel falls back to a generic configuration failure; the local message only mentions scheme/loopback rules. A query relay admitted by the host cannot be entered through the panel, and a snapshot containing it fails panel metadata validation (`grotto-panels-validation.c:64-78`). This is a residual inconsistency in the touched validator, not a newly introduced daemon onion bypass: the authoritative host still refuses onion relays before contact. Align presentation admission with the host's supported public URL contract, without moving signing policy into the panels library.

### F3 — S3, confirmed/executed — Both regenerated POT headers are newly fuzzy

**Where:** `apps/grotto/po/grotto.pot:6`; `gnome/grotto-panels/po/grotto-panels.pot:6`.

The diff adds `#, fuzzy` to both template headers. The six shipped `.po` catalogs have **no** fuzzy entries, and every shipped catalog passes `msgfmt --check --check-format`; these header flags do not make any translated runtime message fuzzy. Nevertheless, an unqualified assertion that all changed catalog artifacts are fuzzy-free would be false. Remove the template flags if the requested no-fuzzy rule includes POT files; otherwise record this template-only exception explicitly. No runtime translation failure was demonstrated.

## Owner-policy and regression checks

- **First-use custody and existing endpoint:** `grotto_control.c:522-536` authorizes automatic creation only with healthy client inventory, readable grants and no `nip46:` inventory/grant row. `bunker_service.c:615-633` serializes its service's load/create work, creates only on `NOT_FOUND`, and refuses automatic replacement when the public endpoint marker exists. Backend errors and invalid keys are not treated as absence. Successful existing-key loads never call the store operation. The executed service probe enabled creation while a key already existed and verified identical transport bytes afterward. The changed marker test passed repeated missing-key starts without replacement. The first-use E2E created custody; headless and restart paths reused it. No pairings are cleared by this creation path; explicit reset remains the separate revocation/replacement operation, now gated against active credential workers (`grotto_control.c:446-478`). This does not claim a cross-process credential-store concurrency test.
- **Secret separation and cleanup:** the key uses nip55l's dedicated `org.nostr.Grotto.BunkerTransport` slot, not the account schema (`nips/nip55l/src/core/signer_ops.c:1538-1631`). The worker's 32-byte allocation is secure, generated/temporary hex is wiped, and the persisted marker is public-key-only (`bunker_service.c:619-632,647-652,715-717`). No new logging of key bytes, tokens or full pairing URIs was found. F1 is the relay-URL exception to the status-sanitization claim, not a failure of transport/account separation.
- **Account identity, hints and revoke:** request-aware handlers are installed before listening (`bunker_service.c:647-655`). `get_public_key` returned the disposable account key and explicitly differed from the transport key in remote-signing and headless execution. Client `perms` feed review hints, not grants (`bunker_service.c:528-543`); the focused flow uses explicit management-granted scopes (`test-bunker-e2e.c:736-744`). Paired admission precedes cached-response delivery, and cached account results re-evaluate exact permission scope (`bunker_service.c:412-432,474-500`). The full flow reached its revoke/replayed-request and explicit-reset checks (`test-bunker-e2e.c:889-906`) before failing the later global audit. This is evidence for those reached assertions, **not** a full replay-safety pass; see the baseline below. No approval-class or always-confirm policy is added by the diff.
- **Relay lifecycle / scoped Nostr-protocol-smells review:** the changed startup/configuration paths use the existing event-driven transport. `bunker_service_reconfigure()` keeps the live session, removes only affected deliveries, retains completed pairing inventory, and recalculates state from EOSE (`bunker_service.c:1040-1089`). The core adds/removes relay membership without resubscribing the whole pool (`nips/nip46/src/core/nip46_session.c:3009-3046`). The full E2E reached assertions that retained relay sockets/REQ counts do not change when another relay is removed or added (`test-bunker-e2e.c:670-678`); its later global audit still failed. Remote-signing independently passed live add/remove, durable pairing and restart. EOSE remains readiness; CLOSED/AUTH become unavailable states, not fake Ready; relay-accepted OK remains required for pairing acknowledgement. No new production polling, arbitrary subscription-close timer, account AUTH signing or send-equals-publish-success shortcut was introduced. The test's log/status waits are observations with failure bounds, not a substitute for relay EOSE.
- **Defaults / empty list:** `grotto_control.c:606-616` seeds only a healthy, uninitialized empty list, preserving nonempty lists. Its four URLs exactly match the pinned [Amber `defaultAppRelays` source](https://github.com/greenart7c3/Amber/blob/621c445a985470f58c9b5575ba2246e36e347fde/app/src/main/java/com/greenart7c3/nostrsigner/models/AmberSettings.kt#L9-L14), independently inspected in this review. They are not reinserted as a connection-failure fallback. Save writes `relays-initialized=true` (`:544-551`), and the executed `/control/empty-relays-persist` case removed the entire signer-wide list, observed `No relays configured`, reconstructed Control1 and confirmed the list stayed empty. Existing per-client relays may still keep their paired clients connected by design (`:487-500`); deleting global defaults is not revocation.
- **Real E2E, not a readiness stub:** `signer/remote-signing` invokes the production daemon and NIP-46 client through a loopback WebSocket relay/private bus, initially with no transport credential and no legacy allowlist. It checks initial Disabled/default persistence, configures through Control1, observes Starting then EOSE-derived LISTENING, obtains a real single-use offer, completes consent/relay-accepted pairing, checks account pubkey separation, and verifies the returned event's signature/content/kind (`test-bunker-e2e.c:714-781,929-983,1210-1224,1284-1294`). Its wire audit observed four unique decrypted RPC requests with four matched replies and one signed event. Relay edits/restart were followed by a working paired public-key RPC. Ready is the panel label for LISTENING; this proves the daemon state/crypto flow, not an automated click on Enable Remote Signing or a native phone pairing.
- **Panels / HIG / markup:** panels render public metadata and dispatch typed host commands; new Add App delegates to the trusted host (`grotto-remote-panel.c:111-117`). They gain no key-storage, secret-token, URI-creation or permission-evaluation implementation. The status row disables markup in both authoritative Blueprint and generated UI. Management-panels checked the exact literal ampersand-containing reason, add/remove persistence and Add App callback; Control1 checked reason propagation. Both requested UI suites and no-secrets passed after supplying their actual prerequisites. No new accessibility/consent defect was established; this is not an Orca or visual desktop review. F2 is the URL feedback inconsistency, not justification for moving daemon authority into the panel.

# GNOME integration and Samba server plan: focused critique

## Context / scope

Reviewed `docs/plans/gnome-integration-and-samba-server-2026-09-25.md` against **only the generated response** in `prompt-exports/oracle-chat-2026-09-25-184820-gnome-and-samba-plan-e603.md` (beginning at its “Wider GNOME Integration + Samba Server: Expanded Plan” heading). The export wrapper, prompt echo, and selected-file context are not treated as baseline plan content. Source checks below are limited to the named seams and directly implicated integration points. This is a design critique, not an implementation or release acceptance result. Findings are ranked by severity; 22 total.

## Findings

### Critical

1. **`SignEvent` is a real return-contract change, not an XML-documentation fix.** Plan **§1.2 D1 / Index #1** (`:446-460`, `:94`); export **§1.2 D1 / Index #1** (`:69-75`, `:34`). Both say the XML is stale, `s` stays unchanged, and implementation already returns signed JSON. The XML at `nips/nip55l/dbus/org.nostr.Signer.xml:6-10` has no prose doc string: its out-arg is named `signature`. More decisively, `nips/nip55l/src/glib/signer_service_g.c:193-196,249-256` calls `nostr_nip55l_sign_event`, and `nips/nip55l/src/core/signer_ops.c:329-360` returns `ev->sig` only. A separate `nostr_nip55l_sign_event_json` already exists at `:363-379` but is **not** the DBus dispatch. The in-tree mock also returns 128 hex characters (`gnome/nostr-homed/tests/integration/mock_signer.c:3-10,55-63,76-83`). Correction: decide whether to change the existing DBus method (breaking semantic contract despite identical `s` wire type; version and migrate consumers/tests) or add a separately named signed-event method and keep legacy behavior. Track 2 D5 cannot parse today’s response as JSON. The comparison to `pam_nostr` length-only acceptance does not make a bare signature intrinsically unsafe for an app-facing signing API; the defect there was accepting it without cryptographic verification.

2. **The proposed Samba `-s` fix would break password provisioning.** Plan **§4.2 B3 / Index #18 / Risks 3** (`:1035-1047`, `:112`, `:1218-1221`); export **§4.2 B3 / Index #18** (`:282-286`, `:52`). `gnome/nostr-homed/src/smb/passdb_tdbsam.c:220-245` already calls `smbpasswd -a -s USERNAME`; its own comment correctly says `-s` is silent stdin mode. `:249-275` invokes `smbpasswd -d` and `pdbedit -x -u` with no dedicated config. Per the [Samba `smbpasswd` manual](https://www.samba.org/samba/docs/current/man-html/smbpasswd.8.html), **`-c <config>`** selects its config and **`-s`** is silent; for [`pdbedit`, `-s <config>`](https://www.samba.org/samba/docs/4.9/man-html/pdbedit.8.html) selects the config. The ambient-config risk is real, but the assertion “without `-s`” and the proposed test “`-s` on every CLI” are wrong. Specify `smbpasswd -c <conf>` while retaining its existing silent `-s`; use `pdbedit -s <conf>`. Test the exact argv for add, disable, remove, and reconciliation.

### High

3. **Token ownership and activation are not implementable as written.** Plan **§2.2 D1/D6, §2.3** (`:619-632,669-699`); export **§2.2 D1/D6** (`:141-151`). The existing user unit at `gnome/nostr-dav/systemd/nostr-dav.service:12-18` has `ProtectHome=read-only` and `ReadWritePaths=%h/.local/share/nostr-dav`, so the proposed `$XDG_CONFIG_HOME/nostr-dav/token` cannot be created under that unit. A separate DBus activation file (`gnome/nostr-dav/systemd/org.nostr.Dav.service:1-3`) launches the same binary outside that sandbox; `nd-application.c:151-158` uses `G_APPLICATION_NON_UNIQUE`, which [explicitly does not own the application ID](https://docs.gtk.org/gio/flags.ApplicationFlags.html). The plan’s “two instances” lock-file is not a substitute for choosing the authoritative activation path. Decide whether the systemd user unit or DBus activation owns the daemon and its token; make both activation routes converge on one UID, one process, one permissions policy, and explicit writable config/data directories. The current unit also needs a config-directory write allowance if it remains authoritative.

4. **A standalone notifier cannot claim GNostr’s `GApplication` identity and simultaneously be suppressed while GNostr owns it.** Plan **§3.3 D4–D5 / Index #14** (`:876-896`, `:108`); export **§3.3 D4–D5** (`:225-230`). GNostr uses `org.gnostr.Client` (`apps/gnostr/src/main_app.c:337`); its registered actions are `notify-open`, `notify-mark-read`, and `notify-reply`, not `app.open-thread` (`apps/gnostr/src/notifications/desktop_notify.c:234-244,479-503`). A `GNotification` action belongs to the sending application, and notifications can activate that application after it exits ([GLib notification API](https://docs.gtk.org/gio/class.Notification.html), [send semantics](https://docs.gtk.org/gio/method.Application.send_notification.html)). A second live daemon cannot simply share GNostr’s unique app ID to route clicks. Give the notifier its **own** ID and a stable GNostr URI/command or DBus activation contract, then add/test the receiving thread action in GNostr. `app://` alone is not that contract.

5. **The session relay’s default federation route is too broad for NIP-29 and DMs.** Plan **§3.2 D4 / §3.3 D2** (`:816-827,858-868`); export **§3.2 D4 / §3.3 D2** (`:214-217,221-224`). “Push upstream everything the user signs” can publish group events to unrelated home relays; treating kinds 9–12 as “notifications-only” ignores that they are actual NIP-29 group messages. The existing group consumer requires the recorded relay URL and matching `h` group tag (`apps/gnostr/plugins/nip29-groups/gn-nip29-group-service.c:919-936`); [NIP-29 requires `h`](https://github.com/nostr-protocol/nips/blob/master/29.md). [NIP-17 uses recipient kind-10050 inbox relays and recommends NIP-42 protection](https://github.com/nostr-protocol/nips/blob/master/17.md), not a generic home-relay fanout. Define event-class/destination routing before #13/#14: group messages stay on the group relay, gift wraps use inbox relays, ordinary events follow explicit publish policy, and the cache must retain relay-of-origin where authorization depends on it.

6. **DAV publish has mutually incompatible outcomes and no durable queue schema.** Plan **Index #9 vs §2.2 D3/D5 and §2.7** (`:103`, `:645-665`, `:756-766`); export **Index #9 vs §2.2 D3/D5 and §2.7** (`:43`, `:145-150`, `:188-198`). Index #9 says “rollback of local store on relay rejection,” but D5 and `test_publish_rollback` keep the local write, mark `pending_publish`, warn, and retry; signer absence also returns DAV success. The proposed SQLite schema has no pending state, signed payload, retry schedule, target relays, or idempotency key. Pick the offline-first queue behavior already described in D5 **or** rollback, not both. If offline-first, make the outbox durable/transactional with the DAV mutation and define what relay OK/quorum clears it.

7. **`GetRelays` depends on an account-refresh producer that is not present in the cited implementation.** Plan **§1.2 D2 / Index #1** (`:461-476`, `:94`); export **§1.2 D2** (`:75-77`). `nips/nip55l/src/core/signer_ops.c:580-589` only returns `[]`; a focused search of `nips/nip55l/src/` and `apps/gnostr-signer/daemon/` found no kind-10002, NIP-65, `home_relays`, or account-refresh handling. The stated “in-memory account record → on-disk account file → asynchronous refresh” is therefore a new storage, network, account-selection, and lifecycle feature, not a small placeholder replacement. Specify that producer and its ownership, or use an existing explicit per-user relay configuration as the simpler initial source; retain `NotFound` when none exists. Do not make Track 3B silently depend on a nonexistent refresh path.

8. **DAV’s inbound filter cannot observe the tombstones its verification requires.** Plan **§2.2 D4 / §2.7** (`:651-659,756-763`); export **§2.2 D4 / §2.7** (`:147-148,190-194`). The proposed REQ includes only kinds `31922,31923,30085`, while both designs require NIP-09 tombstone deletion. Add kind 5, define author/`e` or `a`-tag matching and validation, then test tombstone replay against addressable `(kind,pubkey,d)` identity. Otherwise `test_store_sqlite`’s deletion assertion is unachievable through the stated subscription.

9. **The cited signer IPC lines are not a SO_PEERCRED pattern.** Plan **Background, §3.2 D3 / Index #13** (`:293-302,807-815`, `:107`); export **§3.1–3.2 D3** (`:204-212`). `apps/gnostr-signer/daemon/ipc.c:199-221` unlinks a stale socket, starts UDS, and best-effort `chmod(0600)`; `:240-290` handles TCP loopback and token setup. Neither span reads `SO_PEERCRED`, and a focused search found no peer-credential check in that daemon. The real in-tree pattern is `gnome/nostr-homed/src/auth/auth_peer.c:52-58` (or `auth_boundary.c:127-145`). Keep UID-equality as the intended **new** session-relay check, but specify where accepted connections are checked before libwebsockets processes bytes; mode 0600 and same-UID checks do not defend against a malicious process already running as that UID.

10. **Session-relay logout and socket ownership are unresolved.** Plan **§3.2 D3/D5 and §3.4** (`:803-845,905-909`); export **§3.2 D3/D5 and §3.4** (`:210-217,233-235`). A user manager and socket unit can outlive the graphical login; the plan does not say whether this is a graphical-session service or a per-UID service that may persist under linger. It also mixes socket-unit ownership with daemon fallback bind/unlink and specifies stale-socket unlink only on startup. Choose one owner for `relay.sock`; define stop target, drain/close of upstream subscriptions and queued writes, cleanup of fallback-bound socket on normal shutdown, and a restart test after logout/unclean exit. The socket-unit path must never unlink a live systemd-owned socket.

11. **Direct-relay fallback is a security/privacy policy, not just resilience.** Plan **§2.2 D4 and §3.3 D2/D6** (`:651-659,857-870,896-903`); export **§2.2 D4 and §3.3 D2/D6** (`:147-148,221-230`). Both auto-connect nostr-dav/notifier to `home_relays` if the session relay is absent; `After=nostr-session-relay.service` does not guarantee that the relay is active. Decide whether users can disable direct network access (recommended for local-only/privacy configurations), whether failure is retry/wait versus fallback, and how upstream AUTH, reconnect, and duplicate subscriptions work. Test all three states: not started, deliberately disabled, and temporarily down.

12. **Notifier suppression does not cancel already queued work.** Plan **§3.3 D5 / §3.5 suppression test** (`:889-897,943-951`); export **§3.3 D5 / §3.5** (`:228-230,259-263`). “Subscribes to nothing and posts nothing” requires more than stopping new REQs: an EVENT callback, metadata lookup, coalescing timer, or `GNotification` send may already be in flight when GNostr acquires its name. Specify a generation/cancellation guard checked immediately before send; close subscriptions, cancel grace timers, and withdraw or transfer outstanding notification IDs on name-appear. On name-vanish, re-establish from a persisted cursor with a defined catch-up/no-spam rule. Test name-appear and name-vanish at each asynchronous boundary.

13. **PAM-triggered GVfs unmount crosses the wrong execution context.** Plan **§4.1 A4 / Index #15** (`:973-987`, `:109`); export **§4.1 A4** (`:274-275`). `nostr-smb-mount.sh:16-29,40-71` explicitly says `--mode gvfs` requires the calling desktop user’s session bus; its current CLI supports one `--unmount MOUNTPOINT`, not `--all`. A privileged PAM close hook cannot just fork that helper and assume the right user bus, session, and mount ledger. Make unmount a per-user/session service operation with an explicit list of mounts it owns; PAM can request best-effort teardown without doing GVfs work in-process. Decide what happens when one UID has multiple concurrent sessions.

14. **The DM notification mislabels a random wrapper key as the sender and cannot derive a thread ID.** Plan **§3.3 D3–D4** (`:871-887`); export **§3.3 D3–D4** (`:223-227`). The plan’s “from `<hex8>`” uses the outer kind-1059 pubkey, but [NIP-17 specifies a fresh random wrapper key per message](https://github.com/nostr-protocol/nips/blob/master/17.md). Without unwrap, neither the sender nor counterparty/thread is known. Correct the body to generic “New Nostr DM”; pass only the gift-wrap event ID to GNostr and let its existing decryption path resolve the thread after opening. Do not invent a counterparty target from the wrapper.

15. **Qualified-name admission in `nss_nostr` is a no-op that weakens a clean boundary.** Plan **§4.3 C2 / Index #19** (`:1082-1102`, `:113`); export **§4.3 C2** (`:296-299`). The plan says gated names are “admitted” only so the module returns `NOTFOUND`, which is already the desired outcome: `nss_nostr.c:91-113` delegates lookup and `gnome/nostr-homed/src/identity/identity_common.c:8-20` accepts only `n_` names. Widening this shared identity validator risks changing enrollment semantics for no new lookup result. Simpler complete design: leave Nostr identity admission untouched, verify `DOMAIN\user`/`user@REALM` continue to return `NOTFOUND`, and configure/test `files winbind nostr` ordering. The plan’s §4.4 path `src/common/identity_common.c` is also wrong; it is under `src/identity/`.

### Medium

16. **Milestone E’s gate cannot both depend on “All” and land first.** Plan **Index #21 / Implementation Order** (`:115,1184-1205`); export **Index #21 / Implementation Order** (`:55,348-358`). To make “dep-purity gate lands FIRST chronologically” achievable, change #21’s dependency to the existing authd/PAM build artifacts and baseline allowlist only, land that scaffold before A–D, and re-run/extend it after each track. If the new gate truly depends on every track, it is a final gate, not the first merge. Also distinguish baseline capture from approving new dependencies.

17. **Four of the five requested L rows should be split/re-estimated as XL under the plan’s own sizing rule.** Plan **Index #8/#12/#14/#16/#22** (`:102,106,108,110,116`); export **Index** (`:42,46,48,50,56`). #8 combines live relay ingress with conversion, replay, tombstones, and reconnect; split transport/cursor from format/fold, with external relay acceptance. #14 combines NIP-29/DM subscriptions, GNOME notification/action routing, suppression, and live desktop acceptance; split relay intake from shell UX. #16 claims standalone Samba “shippable” from six files plus `testparm`/smoke mount despite passdb, authority, ACL, and installed-client acceptance; split config/service packaging from end-to-end file-serving acceptance. #22 crosses Debian **and** Fedora packaging of four independently activated surfaces; split per package family plus installed-unit acceptance. Those four fit **XL** (“multi-week with external acceptance”). #12 is large but remains a coherent **L** refactor if the existing relay behavior is frozen and tested separately; do not inflate it merely because it is low-level.

18. **Track 2 D5 need not invent its mock-signer harness, but must update its contract.** Plan **§2.6–2.7** (`:742-766`); export **§2.6–2.7** (`:184-198`). Existing `apps/gnostr-signer/tests/test-dbus.c:55-60,117-143` uses `GTestDBus` and a minimal mock; `gnome/nostr-homed/tests/integration/mock_signer.c:1-10,75-83` and `run_e2e_real_signer_test.sh:39-48` provide another fixture and launch pattern. Reuse the private-bus/test-process plumbing for `test_publish_rollback`, but do **not** reuse the latter mock’s fake 128-hex response as evidence of signed-JSON publish correctness. Use a valid signed-event fixture (and separately exercise denial, no-owner, and late reply).

19. **Preservation gap: the plan drops the export’s explicit “no port env” decision.** Plan **§2.2 D2 / §2.3** (`:633-644,697-710`) vs export **§2.2 D2 / §2.3** (`:143-145,155-159`). Export: port 7680 is fixed **“(no env)”**. Plan: “Port: 7680, fixed” while its file impact only deletes `NOSTR_DAV_ADDRESS`; actual `nd-application.c:57-67` also reads `NOSTR_DAV_PORT`. State whether that override is removed. Otherwise #10 can still have runtime port drift despite a corrected QUICKSTART.

20. **Preservation gap: the named compatibility audit became generic.** Plan **§1.6 Risks** (`:574-584`) vs export **§1.6 Risks** (`:118-123`). Export names `nostr-dav` and the porthome `_ex` consumer for the signed-event contract audit; the plan says only “audit in-tree consumers.” Preserve those named targets and add the existing mock signer/DBus dispatch from finding 1. This is not a request to remove the plan’s detailed tests; it is the specific audit needed before deciding how to change `SignEvent`.

21. **A disabled credentiald unit with no daemon is an unnecessary shipped artifact.** Plan **§4.2 B1 #4/B4** (`:1005-1020,1048-1063`); export **§4.2 B1/B4** (`:277-292`). Both explicitly keep authority inside `nostr-authd` for v1 yet package `nostr-smb-credentiald.service` “shipped but not enabled” with no v1 executable. Documentation can describe the rename-and-lift target without installing a dead unit; reserve its package/unit name and create it when the split daemon actually exists. If the intent is a functional migration placeholder, specify its `ExecStart` and fail-closed behavior instead.

22. **Component-version impact is absent from both plans.** Plan **§5.2 / Index #22** (`:1158-1170`, `:116`); export **§5.2 / Index #22** (`:335-341`, `:56`). The changes affect at least the tracked `nostr-homed` shipped component (`VERSION_MANIFEST.md:18-27`), while `SignEvent` may become a breaking public contract even though nip55l is not yet manifest-tracked. Before merge, apply the repository’s `AGENTS.md` component-version policy per affected component; record bump or “no bump” and source/manifest updates where applicable. This does not require a speculative repository-wide bump in this critique.

## Recommendations

1. Resolve **#1 and #2 before implementation work fans out**: they reverse two load-bearing assumptions (signer result shape and Samba config flag). Make the DBus contract decision first, then align Track 2’s publish fixture and packaging/version decision.
2. Make DAV activation/token ownership, offline queue schema, and relay fallback policy explicit before #5–#9. Keep token validation fail-closed and put the canonical daemon under one lifecycle/sandbox.
3. Define event-class routing and an independent notifier app/action contract before #13–#14. Treat relay provenance, gift-wrap opacity, subscription cancellation, and logout as acceptance cases.
4. Split the four XL rows and land a baseline dep-purity gate **before** the tracks; keep the final integrated gate and installed-system smoke separate. No source or plan rewrite is implied by this report.

## Questions that change the design or order

1. May `SignEvent` change its existing DBus meaning (with a documented compatibility/version transition), or must existing bare-signature clients remain supported through a new signed-event method? This gates Track 2 publish and its mock harness.
2. Is nostr-dav a **systemd user** service, a **DBus-activated** service, or one systemd service delegated to by DBus activation? Which path owns token creation, rotation, and `--show-credentials` under sandboxing?
3. When the session relay is absent or disabled, must DAV and notifications connect directly to remote relays, may the user forbid that, or should they wait/fail closed? Is the relay tied to graphical-session logout or to the per-UID user manager (including linger)?
4. What is the accepted DAV write contract: immediate local 201/204 with durable pending outbox, or error/rollback until a specified relay OK policy is met? How many relay ACKs count as committed?
5. Is the server-side Samba v1 share required to pass real installed SMB-client acceptance before “shippable,” and which process/user owns the materialized mount and the passdb config? This determines #16/#18/#22 sequencing.
6. Is background DM notification allowed to show only an opaque event alert (no sender or thread) until GNostr decrypts it, and what GNostr launch/deep-link contract should the separate notifier use?

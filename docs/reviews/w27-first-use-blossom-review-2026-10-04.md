## Finding

1. **Medium — Marmot file uploads ignore a group's 0x800b server endpoints.** `gnome/groundhog/src/mls/gh-mls-attachments.c:741,749-760` copies the sheet's server list and checks only whether the media policy permits the *Blossom locator kind*; `:708-710` then uploads to that list. `gh_mls_media_dup_servers()` (`gnome/groundhog/src/mls/gh-mls-media.c:730-742`) extracts the policy's verified endpoints but is not used by this path. In a temporary two-fixture extension of `/groundhog/mls-files/send-on-first-use-servers`, I set the adopted group's media-policy endpoint to server A, selected server B in the send, and observed exactly one PUT to B and zero to A. This contradicts the user-facing group promise that its policy names where members fetch and upload attachments (`gh-mls-service.c:4795-4799`, the privacy charter D6 at `docs/designs/groundhog-privacy-ux-charter-2026-09-28.md:63`, and Group Info's “Files stored on … server” copy). A member can thus send a group's ciphertext to an endpoint outside the group's advertised storage policy, and a group with policy endpoints but an empty local list still gets the first-use chooser. Route group uploads through the verified group endpoints when the policy has them (and show those endpoints before Send), or explicitly revise the policy/UI contract if arbitrary member-selected hosts are intended. Add a distinct-policy-versus-selected-server regression. The probe was reverted; no product files were retained in the review commit.

## Checks

- **Core fix:** `Offer` owns the normalized selected-server list and releases it on sheet close/replacement; recipients or group are captured per offer. The DM client and MLS send operation copy the list before asynchronous work, including epoch retries. A later conversation's new offer therefore cannot reuse the previous sheet's selection. Selection performs no upload; both GUI fixtures assert no Blossom requests before Send.
- **Persistence:** the selection handler writes `blossom-servers` via `g_settings_set_strv()` before preview; the new GUI test reads back the selected value. Preferences binds that same key through `bind_list()` in `gh-preferences-dialog.c:1482`, so the choice remains visible there. The test then deliberately clears the setting to verify that the pending upload remains pinned.
- **Revert check:** with only `start_upload()` changed back to read settings instead of the offer's pinned list, both `/groundhog/attachment-ui/first-use-suggested-send` and `/groundhog/attachment-ui/group-first-use-suggested-send` failed waiting for sheet closure; each returned to server selection before a PUT. Restored the reviewed source and reran both full `groundhog-attachment-ui` and `groundhog-mls-files` successfully.

### New finding

1. **Medium — a policy Commit can change the upload destination after the sheet discloses it.** `gnome/groundhog/src/app/gh-attachment-ui.c:569-570` snapshots policy endpoints when the offer opens, and `update_notes()` (`:256-277`) renders that snapshot; the group `notify` handler at `:1095-1101` updates only attach availability. But `gnome/groundhog/src/mls/gh-mls-attachments.c:614-652,733-758` re-reads policy endpoints at Send and on an epoch retry, overriding the list passed from the sheet. In a temporary two-fixture rotation probe, policy A was passed as the old list a sheet would have captured, an admin Commit changed it to B, and a send using that old A list made one PUT to B and none to A. Thus the still-open sheet can say A will learn upload timing/size/IP while B actually does; an epoch retry can also add B after the first upload without fresh disclosure. Revalidate the current policy against the sheet's disclosed host list before any new destination is contacted; if it differs, refresh the read-only note and require another Send/confirmation. Cover a policy change while the sheet is open and one during an epoch retry. The probe was restored; no product source is committed here.

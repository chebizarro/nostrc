# Critique: Groundhog Cordn Support Plan vs. Oracle Export

Date: 2026-11-11 · Reviewer: agent (Claude) · Status: review only, no code changes

## Context and scope

Compared:

- **Plan:** `docs/plans/groundhog-cordn-support-2026-11-11.md` (869 lines, read in full).
- **Baseline:** the generated plan in `prompt-exports/oracle-plan-2026-11-11-120511-plan-cordn-support-i-108a.md`, lines 119–1714 (`### Response` onward, read in full). The composed prompt and selected-file dump above it were treated as context only.

Owner decisions in plan §2 (libmls extraction, generic ContextVM + Signet migration, all optional Cordn features, client-only with gift-wrap default) are taken as fixed and not reopened.

Spot-checks were limited to the seams named below; each cited `file:line` was read on 2026-11-11. Everything else is a reading of the two documents.

Severity scale: **High** = changes a design decision or phase scope; **Medium** = must be resolved before the owning phase starts; **Low** = clarification or wording.

## 2. Under-specified seams, contradictions, incorrect references, missing dependencies

| # | Sev | Finding | Correction / justification |

| 2.1 | **High** | **Transition model vs. in-place engine is unresolved and unsized.** Plan §6.2 makes `prepare_* → accept_transition / discard_transition` the libmls contract ("preparing never mutates the committed group"). The existing engine mutates in place — `mls_group_process_commit(MlsGroup *group, …)` is documented "modified on success" (`libmarmot/src/mls/mls_group.h:583–591`, likewise `_ex`, `_ex_with_psks`, `_by_ref`), and there is **no** `mls_group_clone/copy/dup` anywhere in `libmarmot/src/mls/`. A candidate-state model therefore needs either a deep copy of `MlsGroup` (ratchet tree, secret tree, skipped-key caches, epoch secrets, pending proposals) per processed message, or an undo log. Neither document says which, nor whether Marmot's fifteen call sites (plan §7.1) move to transitions or keep in-place mutation. The export's own §2.2 warning — copying ratchet state can cause key reuse — applies directly to candidate copies. This decides the size of Phase 2 (XL already) and the shape of the snapshot API (`MLSG-COMPAT` must serialize *candidate* state for `cordn_operations.candidate_state`). | Decide in Phase 1, record in the Phase 2 bead: (a) libmls keeps the in-place `mls_group_*` family as public API for Marmot (no semantic change, lowest extraction risk); (b) transitions are an additional layer implemented as `snapshot → load-into-fresh-group → mutate → (accept: swap pointers / discard: wipe)` so no new deep-copy code is written; (c) state the invariant that at most one candidate derived from a committed state is ever accepted, and that `discard` wipes. If (b) is too slow for large groups, that is a measured Phase 8 problem, not a Phase 2 redesign. |

## 3. Details the code disproves, the task does not require, or a simpler design replaces

| # | Sev | Finding | Correction / justification |
|---|---|---|---|
| 3.1 | Medium | **Catch-up ordering: fetch-first/subscribe-second is simpler and strictly cheaper than the plan's subscribe-first/fetch-second + merge.** Plan §6.4 (from export §3.4) opens `msg_sub_many` first, then issues `msg_fetch_many` from the same cursors and merges by `(gid,cursor)`, so that a finite boundary exists without an undocumented "replay complete" frame. But plan §4.1 already states the server's `msg_sub_many` *registers before replay, replays from `after`, buffers live arrivals during replay and suppresses already-replayed cursors*. Given that, `fetch(after=c) → N` then `subscribe(after=N)` is gap-free (anything after N arrives via the stream's own replay) and delivers each record **once**; the fetch result is the live boundary. The plan's order delivers every record in the catch-up window twice, and under gift-wrap default each delivery costs a remote-signer NIP-44 decrypt *before* `(gid,cursor)` dedup is possible (see 4.1). | Replace the §6.4 sequence with: (1) reply subscriptions; (2) `msg_fetch_many(after=committed)`; (3) `msg_sub_many(after=max(fetched, committed))`; (4) wait for `{subscribed:true}`; (5) process fetched records then stream records; (6) live after the fetch boundary. Keep the `(gid,cursor)` merge for reconnects. Keep the plan's "subscribe before publishing" rule — it refers to the *relay* reply subscription, not `msg_sub_many`. Add both orders to `CORDN-ORDER` so the choice is evidence-backed at the pinned server (Q-A). |
| 3.2 | Low | **"Wipe retired media keys" needs no new overwrite logic.** The store already runs with `secure_delete` (`gnome/groundhog/src/store/gh-store-media.h:15`, "secure_delete overwrites evicted pages"). | State in §6.5/§6.7 that `DELETE FROM cordn_media_keys` is the wipe, conditional on `secure_delete` being set at `store_configure` (verify the pragma in Phase 1; it was only seen in a comment). |
| 3.3 | Low | **Migration-runner facts hold.** `store_migrate()` runs each migration inside `store_begin`/`store_commit` with rollback on failure (`gh-store.c:1378–1414`), so the `GH_STORE_MIGRATION_REBUILDS_TABLES` flag in §6.7 is the right minimal change; `PRAGMA foreign_keys` is indeed ignored inside a transaction. Signet's reply path is confirmed to be `nostr_nip17_wrap_dm()` with no `e` association (`signet/src/mgmt_protocol.c:930–947`). | No correction; recorded as verified so Phase 1 need not re-check. |

## 4. Requirements, edge cases, dependencies and architectural problems absent from both documents

| # | Sev | Finding | Correction / justification |
|---|---|---|---|
| 4.1 | **High** | **No gift-wrap demultiplexer; per-wrap remote-signer cost unbudgeted.** Groundhog already has exactly one consumer of the account's gift wraps: `GhDmInbox` keeps one live `{kinds:[1059], #p:[account]}` REQ on the own 10050 relays (`gnome/groundhog/src/app/gh-dm-inbox.h:119–121`); `gh-nip17-inbox.c:226–279` verifies the wrap, calls the external signer's `nip44_decrypt` once, then **requires the inner to parse as a signed kind-13 seal** (`:271–276`, else `INVALID_SEAL`); Marmot Welcomes (kind 444) are routed through a sink (`gh-dm-inbox.h:203–217`). CEP-4 places a signed kind-25910 event directly inside the wrap. Consequences: (a) wherever coordinator relays overlap the 10050 set (likely — users pick the same relays), every coordinator wrap costs one signer round-trip in `GhDmInbox` and is rejected, and every DM wrap costs one signer round-trip in the ContextVM client and is rejected; (b) two identical REQs per relay; (c) NIP-46 signers grant `nip44_decrypt` as a permission (`src/identity/gh-nip46-session.c:49`) and may prompt or rate-limit — with every stream frame, fetch result and RPC reply being its own wrap, an active group generates dozens of signer calls per minute, and decrypt completions can reorder frames. Neither document mentions `GhDmInbox`, a wrap router, or a signer-throughput budget. | (1) Add a per-account **wrap router** below `GhDmInbox` and the ContextVM client: verify wrap → decrypt once → dispatch on inner shape (signed kind 13 → NIP-17 path; signed kind 25910 → ContextVM sink; else reject). Simplest form: a second sink on `GhDmInbox` for signed-25910 inners, and the Groundhog ContextVM host supplies "inbound wraps" from that sink instead of its own REQ when relay sets overlap (ties to 2.2). (2) Make per-wrap decrypt latency a measured quantity in `GH-ENTRYPOINTS` using the mock signer (`tests/mls/gh-test-signer.h` per plan §4.3). (3) State that frame reordering from async decrypts is absorbed by cursor buffering, and that account-generation cancellation drains in-flight decrypts. This touches the NIP-17 path and belongs in Phase 9, not Phase 10. |
| 4.2 | **High** | **`CORDN-ORDER` and `CTX-LIFECYCLE` need a scriptable fake coordinator; none is named.** Equivocation (same cursor, different bytes), cursor gaps, delayed `{subscribed:true}`, lost `msg_post` responses, duplicate deliveries and stream aborts cannot be produced by the pinned TS/Rust coordinators, and unit tests "use no external network" (plan §10). Plan §7.3 lists `test_order.c`/`test_recovery.c`/`interop/` but no in-process coordinator. | Add `libcordn/tests/fake_coordinator.{h,c}`: the 11 methods on `ContextVmServer` + deterministic executor + an in-memory relay driver (libcontextvm needs its own; Groundhog's `tests/relay/wire-relay.h` is app-level), with fault-injection hooks per method. It is also the only way to unit-test `ContextVmServer` replay semantics before Signet. Add to §7.2/§7.3 and the Phase 4 and 8 beads. |
| 4.3 | Medium | **Backup/restore rewinds the MLS sender ratchet.** Plan §8.2 relies on the existing encrypted-store backup for migration rollback, and Groundhog users can restore a backup at any time. Restoring after Cordn sends rewinds `client_state` (sender ratchet, used nonces) → key/nonce reuse on the next send. §6.6 revokes write eligibility on "restart/restore" **only** as part of multi-device sync. | Make the rule backend-wide, independent of sync: on connect, if the coordinator stream is ahead of `committed_cursor` or the own leaf's epoch is behind, force a self-update Commit before any application send. Multi-device then reuses this single rule. (Marmot has the same latent hazard; note it, out of scope.) |
| 4.4 | Medium | **Group/coordinator/account teardown lifecycle is unspecified.** Neither document says what "forget group", "leave group", "remove coordinator" or account deletion do to `cordn_groups.client_state`, `cordn_media_keys`, pending `cordn_operations`, published KeyPackages (`kp_remove` for all refs), in-flight signer calls, and sync tombstones; §6.8 only refuses coordinator removal while groups exist. | Add a "Teardown" operation family to §6.4 (leave → Commit + local wipe; forget → local wipe + tombstone; remove coordinator → `kp_remove` all + wipe inventory; account delete → all of the above, best-effort network, guaranteed local wipe) and corresponding `GH-ENTRYPOINTS` cases. |
| 4.5 | Low | **Poll closing time trusts the sender.** `created_at` in the unsigned envelope is sender-chosen; validating a vote's `created_at` against `endsAt` (§6.4) lets a voter backdate. The only authoritative order is coordinator cursor/`at`. cordn-web's behaviour decides interop. | Record the trust model explicitly; prefer coordinator `at` for closing with `created_at` display-only, unless cordn-web parity (Q-F) forces sender time. |
| 4.6 | Low | **Testability of async signer in libcontextvm is only implied.** The "deterministic executor" (§6.3) covers scheduling, but signer/decrypt completion ordering, cancellation mid-decrypt and account-generation checks need a scriptable fake signer at the libcontextvm level (not only Groundhog's `gh-test-signer.h`). | Add `libcontextvm/tests/fake_host.c` (executor + signer + relay driver) as the shared harness for `test_client_server.c`, `test_stream.c` and 4.2's fake coordinator. |

## 5. Questions that would change the design or implementation order

| # | Question | Why it matters |
|---|---|---|
| Q-A | Does the pinned coordinator's `msg_sub_many` replay from `after` and register before replay, as plan §4.1 asserts? | Decides 3.1 (fetch-first vs. subscribe-first), the `CORDN-ORDER` cases and the per-wrap signer cost in Phase 8. |
| Q-B | Who owns the wrap router — an extension of `GhDmInbox` or a new layer under both — and do coordinator relays default to the account's 10050 relays? | Decides 4.1; moves NIP-17 regression risk into Phase 9 and determines whether the ContextVM host needs an "inbound wrap source" (2.2). |
| Q-C | Does libmls keep the in-place `mls_group_*` API for Marmot, with transitions layered on snapshots (2.1)? | Phase 2 size and the snapshot API's role in `candidate_state`. |
| Q-D | Is the relay transport a host interface (2.2)? | Phase 4 public API; Phase 7's `relay_pool.c` row; whether Groundhog's AUTH/Tor policy applies to Cordn traffic. |
| Q-E | Is one remote-signer `nip44_decrypt` per inbound wrap acceptable under the privacy charter and NIP-46/NIP-55L signer UX? If not, is Cordn limited to accounts whose signer can batch or run locally? | Identity is the account key (KeyPackage evidence is the signed `kp_publish`), so no session key can substitute; the answer may gate the backend per signer type. |
| Q-F | Which time authority closes polls — sender `created_at` (cordn-web parity) or coordinator `at`? | 4.5; interop with cordn-web vote acceptance. |
| Q-G | Where does the GLib host adapter live, and may Signet take a nostr-gobject dependency (2.5)? | Phase 6/7 packaging in both CMake and Meson. |
| Q-H | Will Groundhog ever enable 21059 (2.4)? | If "never", drop it from Groundhog's negotiation path and interop gates; keep only in libcontextvm/Signet. |

## Recommendations (ordered)

1. **Before Phase 1 closes:** answer Q-A/Q-C/Q-D; amend plan §6.2 (in-place + transition layering), §6.3 (host relay transport; single kind-parameterized NIP-59 family; transient vs. permanent decrypt errors), §6.4 (fetch-first catch-up; teardown family), §6.1 (no 21059 for Groundhog RPC).
2. **Phase 4 scope:** add the libcontextvm fake host (executor, signer, relay) and GLib adapter placement; Phase 8 scope: add the fake coordinator (4.2).
3. **Phase 9 scope:** add the wrap router (4.1) and the ratchet-rewind guard (4.3) to the `GH-ENTRYPOINTS` gate; add the cumulative-shape diff to `GH-STORE` (2.3).
4. **Leave unchanged:** everything in §1 — the plan did not lose export content; do not trim its specificity.

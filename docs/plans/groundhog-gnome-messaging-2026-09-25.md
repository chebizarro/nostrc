# Groundhog: GNOME messaging implementation plan

**Status (implementation in progress, 2026-09-27):** The opt-in `org.nostr.Groundhog` GTK shell builds and has metadata-only account selection, signer reachability and accessible read-only states (`3669e3c2`, `ac1ceb05`, `d4447c1f`, `64752709`; version 0.4.1 after the GResource launch fix), but no live conversation or message transport. Partial standalone-core `nostr-gtk` isolation landed in `849d90e0`, while four widgets remain Gnostr-coupled. The static signer adapter and typed approval contract remain unlinked to the app; per-operation private-bus cancellation now revokes only that operation's pending approval without blocking the UI on connection setup (`553bfed5`); the service's disconnected-sender guard (`f2ae3b58`) has a deterministic counterfactual pre-cleanup regression (`c6a7b877`). The Groundhog-owned URL-scoped relay foundation is now linked into the app only for the active account's own kind-10002/10050 relay-list discovery (generation-bound, torn down on switch, opt-in `discovery-relays`; version 0.4.0); no conversation subscription or publication path uses it yet; core inclusive same-second reconnect replay, newest-first dedup and nonblocking EOSE handling landed in `fc8fdfc0` and `8a2d8fd3`, and the 1,024-ID bounded cursor/replay cache (`01c1214d`) retains all unseen same-second events while allowing at-least-once redelivery after eviction. The libnostr service thread now requests actual socket shutdown on scope cancellation (`e8633a45`), with a local relay-side close regression; delivery of a separate Nostr `CLOSE` frame is not guaranteed. Marmot draft-10 AppDataUpdate parsing (`7938f669`) and an internal same-epoch admin-policy transition helper (`85ebfaf3`) are not wired into live Commit processing; the adopted producer remains OFF. The earlier kind-30443 KeyPackage migration (`nostrc-s2bz`) and Nostr dispatcher (`nostrc-1v65`) are baseline, not end-to-end readiness. Epic `nostrc-qp24` and release gates remain open.

**Date:** 2026-09-25 · **Target:** `gnome/groundhog/`

## Goal and launch contract

Build **Groundhog**, a standalone, approachable GTK4/libadwaita messaging app in the `nostrc/gnome` distribution. A single recent-conversations list leads to NIP-17 private DMs, NIP-29 relay-hosted groups, and Marmot MLS encrypted groups. Apple Messages supplies the calm list/detail and bubble inspiration; GNOME HIG, adaptive navigation, keyboard/accessibility behavior, and system settings take precedence over visual imitation. Launch includes group creation/join/invite, membership and admin management for both group protocols; local, NIP-46 and NIP-55L signing where available; notifications while the window is open or closed within an active GNOME session; and explicit failure states rather than apparent success after a send.

The user fixed three choices: **share stored identities, but give Groundhog its own active-account selection**; **include member/admin controls at launch**; and **support all three signer modes**. These are release criteria, not optional stretch work. Plan implementation with independently testable work items; do not ship a UI-only facsimile of an unready protocol path.

### Done when

A fresh install can choose an existing Gnostr identity without moving Gnostr's current account, receive and send standards-conformant messages through each backend, manage a group with both an authorized and an unauthorized identity, survive restart and relay interruption without corrupting MLS state, and deliver a privacy-safe notification that opens the correct conversation. Automated, local-relay, third-party interop, side-by-side, and GNOME manual gates in §Verification all pass. Unmet adopted-Marmot conformance is a release blocker, not a hidden compatibility claim.

## Architecture and ownership

### Layering and contracts

`Groundhog UI → Groundhog conversation model/services → nostr-gtk and nostr-gobject + NIP libraries + marmot-gobject/libmarmot → libnostr/relay pool`. No Groundhog target links `apps/gnostr/src` or plugin objects. Reuse the installed library types; **extract only genuinely reusable widget/utility dependencies** from `nostr-gtk` where its app-header coupling blocks Groundhog, with existing Gnostr caller behavior preserved. Port DM/NIP-29 control flow against shared APIs rather than link private Gnostr UI classes or create a premature protocol-erasing “group service.” A one-line conversation-list interface is shared; authority, IDs, member semantics, and event state remain backend-specific.

Proposed app modules under `gnome/groundhog/`: `GhApplication`/`GhWindow`; identity and signer adapter; one relay coordinator; `GhDmService`, `GhNip29Service`, `GhMlsService`; `GhConversation`/`GhMessage` and a merged `GListModel`; list/chat/onboarding/new-chat/group-management/preferences widgets; notification service; schema, desktop/appdata/icon, tests and distro unit/packaging. `GhConversation` carries a typed backend key (`DM` canonical sorted participant-set key from rumor author plus all `p` tags, `(normalized relay URL, group id)`, or MLS group id), title, preview, activity time, unread count, loading/error and privacy state. Never coalesce NIP-29 groups merely by `h`, or equate an MLS group's routing `h` with its stable group identity. The sender is message metadata, not a speaker-dependent room key. Each backend emits account/generation-tagged change signals; a main-context-owned `GhConversationStore` serializes updates to stable row objects, reorders them and emits `GListModel::items-changed`; only this model binds the sidebar. Test simultaneous EOSE/live updates, unread reorder and stale callbacks after account switch. The UI dispatches via backend capability interfaces and renders precise unsupported/rejected states; it does not mutate protocol state directly.

The app has one fixed `org.nostr.Groundhog` GApplication/desktop identity, a matching desktop filename, icon, metainfo, GSettings schema, and DBus activation. Register `app.open-conversation` and URI handling with validated, account-scoped targets; do not copy Gnostr's split app-ID situation. Bridge hooks install before any identity/pool/GTK object consumes them and are invalidated after cancellables/subscriptions drain. Either make the global bridges process-owned with a single installer or add an instance-safe context to shared APIs; no simultaneous Gnostr/Groundhog instances in one process are assumed.

### Identity, signing and storage

Discover explicitly shared identities through the signer-owned `org.gnostr.Signer/identity` metadata contract (`gnome/seahorse/secret_store.h:16-73`), preserving legacy migration and Gnostr compatibility. Groundhog must not read or duplicate an nsec: local-key signing and NIP-44 operations go through the approval-gated `org.nostr.Signer` service, with selected-pubkey verification on every result. Add only a narrow metadata accessor/adapter if needed; do not extract Gnostr's old keystore implementation as a new secret-reading client. Groundhog's `current-npub`, signer preference, window state and notification settings live under its own GSettings schema; Gnostr's current identity is never overwritten. Link/import is opt-in, with confirmation before shared-key deletion or replacement; switching identities cancels old subscriptions/RPCs, clears decrypted memory and pending UI actions, then opens the new account's stores before resubscribing.

Groundhog's schema contract is explicit: `current-npub` (default empty), `signer-method` (`auto`, `local`, `nip46`, `nip55l`), `notifications-enabled`, `notification-privacy` (`hidden` default, `sender`, `preview` opt-in), `sound-enabled`, and window size/maximized state. Keep bunker credentials in signer-owned secret storage, never a bunker URI/secret in Groundhog GSettings. Preferences show both requested and currently resolved signer method; onboarding offers existing-key selection/import or a clearly labelled read-only mode. A missing/locked signer presents an `AdwStatusPage`/banner and disables the composer without hiding recoverable history. The signer adapter is keyed by **verified selected pubkey and declared capability**, not by `gnostr_identity_get_current().signer_type` inference. Reuse `nips/nip46` core and GLib layer for bunker URI/connect, `sign_event` and NIP-44 RPC (`nips/nip46/include/nostr/nip46/nip46_client.h:68-122`, `nip46_client_g.h:1-56`), extending GLib async coverage/cancellation where missing. Reuse the existing NIP-55L DBus proxy pattern (`apps/gnostr/src/ipc/gnostr-signer-service.c:224-245,719-741,983-1020`) only when the service is actually available on the host. Local signing is performed by the signer service; Groundhog receives no secret bytes, and its logs, caches and GSettings must never contain an nsec or bunker credential. Auto-selection may prefer an explicitly configured signer, then local, then a verified available external signer; a requested method never silently falls back to a **different pubkey**. Validate returned signed-event pubkey, id, signature and requested payload before publishing. For NIP-46, bind bunker session responses to the configured identity and treat timeout/cancel/permission denial as distinct errors. For NIP-55L, call it only if its DBus capability exists; “where available” means a transparent unavailable state elsewhere, not fake support. A missing signer makes already-decrypted public NIP-29 history readable, but encrypted new data may be unavailable; disabled send controls explain why.

Private caches are Groundhog-owned, per account, under XDG data/state directories: validated DM rumors, unread/read position, tracked NIP-29 groups, MLS state, publication outbox, and notification cursors. Do not reuse Gnostr's plaintext `dm-rumor-cache.jsonl` or `marmot.db`; avoid cross-app cache poisoning and concurrent MLS writes. DM cache must be integrity-bound to source wrap/event id, verified sender, recipient account, and protocol version, with atomic writes, restrictive permissions and corruption skipping. MLS state and key packages are **secret-bearing**: require an encrypted-at-rest storage design (key from Secret Service or equivalent, secure backup/restore policy) and a crash-consistent transaction/snapshot contract before launch. If the selected SQLite backend cannot support the adopted protocol's staged/rollback state (`libmarmot/src/storage_sqlite.c:1203-1228` currently reports unsupported for snapshots), implement the missing backend capability rather than treating `0600` permissions alone as encryption. Never auto-import Gnostr MLS database into Groundhog; multi-device/restore requires an explicit interoperable story or an honest single-device limitation in onboarding.

### Relay, process and notification lifecycle

Use a process-owned relay coordinator with **separate pools by exact relay scope**: one for the active account's kind-10050 DM/Welcome inbox, one per distinct NIP-29 authoritative relay, and one per distinct MLS routing-relay set (reuse a pool only when its URL set is identical). This is a deliberate correction to the draft's one-pool optimization: `gnostr_pool_query_urls_async` already targets one-shot queries (`nostr_pool.h:153-174`), but `gnostr_pool_subscribe` chooses the first connected relay and `gnostr_pool_subscribe_multi` follows *all* current and future connected relays (`nostr_pool.h:230-313`), so handles and post-receive provenance alone cannot restrict live REQ destinations. Bound pool/relay counts; a later per-subscription URL-targeting API may reduce sockets only after proving identical routing. Keep separate subscription handles/EOSE and cancellation generations for DM inbox, NIP-29 group relays and MLS routing relays; test REQ destinations and late relay additions. The dispatcher validates outer kind/id/signature/tag shape before routing. A kind-1059 inbox subscription feeds NIP-17 and Marmot Welcome classification after one verified unwrap; kind-445 MLS messages are direct `#h` relay events, not gift wraps. Deduplicate outer events by event ID and source, but Marmot state by authenticated MLS message bytes/identity, not the outer 445 ID: two signed envelopes may carry the same Commit. Test the same MLS bytes under distinct 445 IDs across relays/restart. Maintain bounded EOSE-aware backfill, revoke generations before cancellation, and surface AUTH/CLOSED/OK/reconnect; relay OK is not MLS consensus.

Groundhog is the notification owner for its accounts. Ship a GNOME user-session background mode (single GApplication instance held by a managed user service or equivalent lifecycle) so closing the window does not end subscriptions; opening/notification activation presents the same instance. Choose service activation/stop/account-generation ownership in W0 and establish it in W3 before protocol callbacks register. It must be opt-out, resource-bounded, and stop on logout. A build without it does **not** meet launch criteria; foreground-only is for development packages. Do not ask the keyless proposed `nostr-notify-daemon` to decrypt DMs or share Groundhog's app ID. Because `nostr-notify-daemon` has shipped and currently watches only Gnostr, coordinate explicit **per-account/protocol ownership** over the session bus before enabling Groundhog background notifications: Groundhog owns its active account while its service is present; the daemon suppresses overlapping IDs using name-owner/generation checks, with a tested loss/restart handoff and no duplicate alerts. Existing daemon behavior is not yet sufficient.

Use `GNotification` under the matching app ID/desktop entry (`DBusActivatable=true`, `X-GNOME-UsesNotifications=true`), one stable notification ID per conversation and a tracked ID→account/conversation map. The default `app.*` action opens the exact conversation even from a cold/windowless start; withdraw when that conversation becomes visible and focused/read, on account switch, or on logout. Throttle/coalesce busy conversations and give per-app/per-conversation mute settings; limit actions to useful controls (at most three) and provide equivalent in-window actions. **Default to hidden content on lock screen** and a generic encrypted-message body; explicit user opt-in can show sender or preview after authenticated decryption. Never derive DM sender from the gift-wrap outer pubkey, show content after a failed decrypt, or expose MLS group identity in pre-decrypt alerts. Check portal-supported options before using `im.received`, inline reply or hide-on-lock-screen hints; `GNotification` remains the portable baseline. This follows [GNOME HIG](https://developer.gnome.org/hig/patterns/feedback/notifications.html) and [GIO's app-ID/desktop rules](https://docs.gtk.org/gio/class.Notification.html).

## Protocol flows and failure behavior

### NIP-17 DM

Use [NIP-17's current room/send/relay rules](https://github.com/nostr-protocol/nips/blob/master/17.md). A room key is the **canonical sorted set** of each rumor's author pubkey and all `p` recipients, independent of which participant authored that message, so changing participants creates a new history; the latest `subject` tag names the room. Start with one-to-one and small multi-recipient rooms using that same model, rather than mislabelling NIP-17 as a moderated group. Compose kind-14 plaintext rumor (and kind-15 encrypted-file rumor when attachments are enabled), compute its id, seal kind 13 signed by the **real account signer** with NIP-44 encryption to each recipient, then for **each recipient and the sender's own copy** create a distinct kind-1059 wrap: fresh random wrapper keypair, outer NIP-44 encryption using that ephemeral private key and that receiver's pubkey, ephemeral signature, recipient `p`, independently randomized seal/wrap timestamps. This corrects the draft's incomplete “one recipient wrap” and its implicit sender-key outer encryption. Wipe ephemeral private keys after use; do not route them through NIP-46/NIP-55L. Verify both the event signature and seal-signer/rumor-author equality before admitting a received rumor.

Discover each receiver's signed kind-10050 inbox list and publish **only** to that receiver's listed relays. If absent, stop with “recipient has not configured DM inbox relays”; **do not** use a kind-10002/home-relay fallback (the old Gnostr pattern conflicts with current NIP-17). Use the sender's own 10050 relays for the self-copy. Provide an onboarding flow to publish/configure Groundhog user's 10050 list before claiming receive readiness. Keep per-recipient publication state (signed wrap, target list, accepted/rejected OKs); a partial fanout is reported as partial rather than re-encrypting or duplicating. Receive on own 10050 relays with overlapping bounded backfill/live subscriptions; verify targeted `p`, unwrap with the active signer against outer ephemeral pubkey then seal pubkey, validate kinds and rumor identity, dedup, cache, update list/unread and notify. Unknown sender or signer unavailable leaves a bounded retryable encrypted item; no fabricated plaintext. The common dispatcher distinguishes kind-14/15/5/7 rumors from Marmot kind-444 Welcome and rejects unsupported kinds safely. Deletion/edit/disappearing semantics and reaction display follow NIP-17 if exposed; do not imply local delete removes remote wraps. Kind-15 requires authenticated encrypted upload, MIME/size/hash checks, no plaintext temp files, and tests before enabling its attachment button; do not borrow Gnostr's upload widget as proof of secure file support.

### NIP-29 relay groups

A group key is `(canonical relay URL, group id)`; its relay is authoritative. Initial query and live subscription fetch kinds 39000–39003 by `#d` and 9–12 by `#h` **from that relay**, with provenance and relay `self` signature checks for snapshots; accept that kind-39002 membership may be absent/partial and say “members not fully available,” never “0.” Render kind-9 root chat and 10–12 replies/threads; only offer reply composition when it is correctly tagged/signed for the group's `supported_kinds`. Persist manually followed groups per account, not shared Gnostr plugin JSON; optional kind-10009 group-list discovery is separate from authority. Use generation-guarded refresh, deterministic `(created_at,id)` ordering, dedup and EOSE; maintain recent same-relay event prefixes for recommended `previous` tags. Check group migration/fork kind-10009 when the authoritative relay is unreachable; **inform and ask before changing relay identity**, preserving the old history as a separate branch ([NIP-29](https://github.com/nostr-protocol/nips/blob/master/29.md)).

Create 9007, join 9021 (invite code), leave 9022; offer member/role add/update 9000, remove 9001, metadata 9002, moderation delete 9005, invite creation 9009, and role display from 39001/39003. The spec leaves role capabilities to relay policy; therefore an “admin” badge is **not proof of a particular permission**. Gate dangerous affordances on authenticated relay snapshots and known policy, confirm destructive actions, but let a clearly privileged user attempt an operation when exact role policy is unknown and surface a rejecting OK without local mutation. Every event has required `h`, the correct operation tags and optional `previous` references, is account-signed, and goes to the one authoritative relay. A 9021 join may receive a **rejecting** relay `OK` even when admission is pending review: parse pending-review, final denial/payment, `duplicate:`, and unknown reasons. Do not treat rejection as successful join; observe later authoritative 9000/9001 (and available 39002) before member-only controls. Test pending rejection→later admission separately from final rejection and duplicate. Likewise wait for authoritative state after admin action. Pending/rejected/duplicate/closed/private/restricted states need distinct, non-jargon UI copy. Do not infer complete member count from a partial snapshot, or auto-migrate a group after a relay timeout.

### Marmot MLS groups

Target the [adopted Marmot specification](https://github.com/marmot-protocol/marmot), especially its [Nostr transport](https://github.com/marmot-protocol/marmot/blob/master/transports/nostr.md), [registries](https://github.com/marmot-protocol/marmot/blob/master/foundation/registries.md), and [group-state lifecycle](https://github.com/marmot-protocol/marmot/blob/master/protocol-core/group-state.md). **Prerequisite:** audit `libmarmot`/`marmot-gobject` against the adopted profile, not just legacy MIP tests. Build on the landed addressable **30443** KeyPackage publication/fetch, stable `d` slots, `i` KeyPackageRef checks and account write-capable kind-10002 routing. Do not count this as complete adopted-profile conformance: the producer is opt-in/OFF until app-component/AppDataUpdate engine support, and legacy-443 coexistence/read policy plus vector/interop tests remain explicit gates. A Welcome is a kind-444 rumor sealed/wrapped in kind 1059, addressed to the recipient's kind-10050 inbox. Validate the claimed KeyPackage event/ref and receiver identity before accepting; send through the recipient's inbox relays only. Direct kind-445 messages use a fresh ephemeral signing key, exactly one `h` and optional valid expiration, signed id verification **before** outer decryption; subscribe by current/retained routing IDs on the group's routing relays, not the inbox. Reject malformed base64 or under-28-byte content, retain deferred candidates per the adopted epoch/rollback policy, and never mark resource-refused/undecryptable input terminally seen.

`marmot-gobject` needs an additive async boundary for “produce unsigned message/evolution → ephemeral sign → persist signed event and staged state → publish/acknowledge → commit or rollback/retry.” The current header has send/process but no save-created or add/remove-member methods (`marmot-gobject-client.h:135-325`); implement and test those wrappers over `libmarmot/include/marmot/marmot.h:179-238` rather than reaching through private client storage. **Separate app-message persistence from group-state staging:** `marmot_save_created_message` records a signed message/recency (`libmarmot/src/messages.c:477-540`), not a staged MLS Commit. A single encrypted transactional record owned by the Marmot state engine must atomically capture the pre-commit canonical state or rollback snapshot, staged state, operation ID, signed event JSON, inner payload, routing target snapshot, and per-target attempt status before any network send. Define durable `Stable → PendingPublish → Merging/Recovering → Stable or Unrecoverable` transitions per the adopted group-state spec; on restart classify each persisted state and resume/reconcile without inventing a second Commit. Publish the **same signed event** to all permitted snapshotted relays; distinguish first accepted OK from completing fanout; never advance canonical MLS state merely because JSON was created or a socket write returned. On timeout, preserve pending state and retry idempotently; on conflict/concurrent commit, invoke the adopted convergence/repair path instead of blindly applying an epoch. Crash tests must cut at record-write, first OK, later fanout, apply and rollback boundaries for both ordinary messages and state-changing commits.

Launch administration covers invite/add member by fresh verified 30443 package, remove member/account, group metadata and admin-role changes, with the exact authorized action derived from adopted admin policy and current MLS group state. Keep **owner** and **admin** visibly distinct where policy distinguishes them (`libmarmot/include/marmot/marmot-types.h:564,605-606`); do not assert that a creator can transfer ownership unless adopted policy and library API support it. Add a missing GObject API or low-level implementation where needed; a disabled button is acceptable only for a genuinely unauthorized user, **not** as the implementation of the user's launch requirement. Every change produces an MLS commit/evolution event, waits for the publish lifecycle, and tests removed members cannot decrypt later epochs. Group routing/key-package/Welcome flows retain separate relay and signature rules. Encrypted media follows the adopted feature only after its v1/v2 compatibility is proven; do not conflate legacy MIP media with current conformance.

### Cross-cutting errors and edge cases

| State | Required behavior and proof |
|---|---|
| Signer absent/denied/timed out | Read-only or action-specific error; keep unsent draft and cancellable operation; never publish under a stale/different identity. Retry after verified reconnection, not a silent timer loop. |
| Relay rejects OK, CLOSED, AUTH or disconnects | Preserve exact endpoint outcome; NIP-29 state unchanged until authoritative snapshot; DM self/recipient wrap fanout reported separately; MLS staged state/outbox retained for safe retry. |
| Malformed/replayed/duplicate event | Validate id/signature/kind/tags and source before side effects; dedup envelopes by event id plus account/backend scope and MLS state by authenticated message identity, not merely UI row; bound memory and persistent cursors. |
| EOSE/backfill/live race | Merge through one admission path with overlap and stable ordering; no missed event at cursor boundary; stale generation callbacks ignored. |
| MLS unavailable epoch or storage error | Retry/defer within protocol limits; show “Unable to decrypt yet” without leaking details; do not advance canonical state or permanent-seen cursor. |
| Cache corruption or disk full | Skip isolated invalid DM lines; fail closed for MLS state transaction, retain recoverable pending data; no success UI until durable write/relay criteria hold. |
| Account switch/logout | Cancel signer and relay work, clear plaintext buffers and notification IDs, close prior account's DB and subscriptions before opening new ones. |

## Tradeoffs, corrected draft assumptions and risks

1. **Port app-layer services, not Gnostr linkage.** This duplicates some dispatch/cache logic but avoids private UI/plugin dependencies; a later shared-service extraction is justified only after both consumers stabilize. Extract shared crypto/keystore/widget primitives now where they have a clear installed API.
2. **Adopted Marmot over legacy convenience.** The draft treated `marmot-gobject` as ready for admin/persistence and kind 443 as current. Source and current spec disprove both; kind-30443 KeyPackages have since landed, but the adopted producer is gated OFF. Compatibility decision, app-component support, staged publish, snapshots and encrypted state remain prerequisites; no claims of current interop until third-party vectors pass. This is the largest schedule risk.
3. **Use existing NIP-46.** The draft's new `GhNip46Client` is replaced by an adapter around `nips/nip46`; exact asynchronous NIP-44 coverage and active cancellation remain a bounded gap.
4. **Correct DM routing/crypto.** Draft's kind-10002 fallback, single receiver wrap and sender-key outer encryption contradict current NIP-17. Require per-recipient plus self wrap, recipient 10050 only, ephemeral outer encryption/signature. Do not copy Gnostr's sender-signed helper.
5. **Keep notifications private and singular.** Unlike the draft's default sender-only preview and unconditional `nostr:` claim, default to generic content, use one owner app ID and the existing dispatcher/Handler2 with an app action for notifications. Background mode is required for window-closed alerts; the shipped distro notifier must prevent duplicate ownership.
6. **Relay-scope isolation over one shared pool.** Separate URL-scoped pools consume more connection resources but enforce current live-REQ routing correctly. Cap/observe pool counts and reuse only identical relay sets; a future targeted-live-subscription API can recover the socket optimization without merging protocol authority.
7. **Storage and multi-device are security risks.** `0600` unencrypted SQLite is insufficient for secret-bearing MLS state. Encrypt and transactionally stage it. Do not promise cross-device MLS continuity from shared account keys alone; document supported single-device/restore behavior until interoperable multi-device work is proven.
8. **Toolkit version floor.** `AdwNavigationSplitView` exists since libadwaita 1.4; choose the minimum *stable* version that supplies every selected widget (including dialog) and is present in the target GNOME distribution, then pin/test it. Do not use the online 1.11.alpha API level as a shipped dependency.

## Version and release assessment

The manifest currently lists `nostr-gobject` as stable `1.0.0` and `nostr-gtk` as `1.0.1` after the standalone-core build PATCH, `libmarmot` as `0.3.1` after the fail-closed wire-codec PATCH, `marmot-gobject` as stable `1.1.0`, `nostr-homed` as `0.2.2`, and new Groundhog as `0.1.0`; NIP-17/29 are **not** independent entries (`VERSION_MANIFEST.md:10-27`). W0/W8 must adjudicate each actual diff, update **both** CMake and Meson authoritative values where listed, and change manifest Declared version in the same implementation commit. Groundhog's new `0.1.0` CMake source and manifest row landed with the opt-in shell in `3669e3c2`. Do not update Latest release/tag columns before a matching published component tag. No component version bump is required for this plan/bead-only update; each implementation bead must assess its own shipped surface and release notes. The landed kind-30443 migration is a baseline, not a version bump to repeat.

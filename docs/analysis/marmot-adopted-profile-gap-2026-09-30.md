# Marmot adopted-profile interoperability gap: libmarmot 0.11.0 vs MDK

Research snapshot: 2026-09-30 (Pacific). Bead: `nostrc-ltmg`. This is source analysis, **not** a successful adopted-profile interop test. Upstreams were shallow-cloned outside this repository to `/tmp/nostrc-ltmg/`; no upstream code is vendored here.

## Decision in brief

Target **the adopted Marmot spec and MDK v0.11.0** as the first release gate, while pinning v0.9.0 as a historical **dictionary-engine, pre-current-proof** incompatibility probe. Preserve the proven MDK v0.8.0/MIP-era path as an explicitly selected **legacy group profile**, not as a heuristic decoder or a claim that v0.11.0 speaks v0.8. Do not publish adopted KeyPackages or advertise general White Noise compatibility until an external v0.11.0 peer can create, join, message and change membership with Groundhog in both directions. Current libmarmot can parse/produce some adopted KeyPackage bytes internally; it **cannot join or create an adopted group**. This is a release blocker, not a cosmetic feature gap.

The W23 result remains narrower: libmarmot 0.11.0 exchanged legacy-profile Welcomes, messages and Commits with **MDK v0.8.0** when `allow_unproven_members` was enabled; its safer default deliberately rejects unproven MDK 0.8 members in several flows, and a bystander Add can strand it. See [W23 results](marmot-mdk-interop-2026-09-30.md) and the [pinned harness](../../tests/interop/mdk/README.md). It did not test the post-0.8 engine.

All protocol claims below refer to the adopted snapshot unless marked *MDK implementation* or *legacy*. MDK release compatibility of **generated Swift/Kotlin source, native libraries, C headers, CLI JSON and local SQLCipher schema** is a different axis from on-wire Marmot compatibility. The v0.11.0 guide requires one immutable binding cohort, upgrades account schema 89→98, and forbids downgrade; it does **not** provide a v0.8-to-adopted MLS group migration procedure. The old Flutter [`whitenoise` v2026.5.22+25 release](https://github.com/marmot-protocol/whitenoise/releases/tag/v2026.5.22%2B25) explicitly required users to recreate old groups after its protocol/storage reset. Do not confuse that app reset with a safe general wire migration.

### What changed after MDK 0.8

- **0.9.x:** `cgka-engine` became the group-state engine and the MIP-01 monolith gave way to authenticated `app_data_dictionary` components and AppDataUpdate. v0.9.0 itself emits the now-superseded `0xf2f1` proof v1, so **0.9.0 is not wire-equivalent to today's adopted proof-v2 profile**. Current KeyPackages are `MLSMessage(mls_key_package)` rather than bare KeyPackage bytes; current new groups require `0x8009` and other adopted components/capabilities. The [engine profile builder](https://github.com/marmot-protocol/mdk/blob/946e0547485c9a2c393c2048ec3a968fd50fb441/crates/cgka-engine/src/engine.rs) defaults to `Current` and refuses production creation of `Legacy`; the [KeyPackage parser](https://github.com/marmot-protocol/mdk/blob/946e0547485c9a2c393c2048ec3a968fd50fb441/crates/cgka-engine/src/key_package.rs) requires a valid profile proof. The [0.9.21 release](https://github.com/marmot-protocol/mdk/releases/tag/v0.9.21) already rejects relay KeyPackages advertising RFC 9420 implicit default capabilities as explicit ones.
- **0.10.x:** consolidated release cohorts for Rust/`wn-agent`/MarmotKit/Marmot C, forward-only account-store migrations, broader runtime/host API, recovery and media. Do not assume all 0.9.x or 0.10.x tags are wire-equivalent: inspect proof and component carriers per tag. The 0.10.0 label is not by itself a second Marmot group wire version: the [0.10.0 notes](https://github.com/marmot-protocol/mdk/blob/v0.11.0/docs/release/0.10.0.md) call it a *client/binding compatibility cohort*.
- **0.11.0:** recovery, durable spill, encrypted NIP-88 polls, audit v5 and release-artifact changes. Existing peer text/MLS transport is not described as rewritten, but a full White Noise UX must render and vote on polls sent by peers. Follow the [release notes](https://github.com/marmot-protocol/mdk/blob/v0.11.0/docs/release/0.11.0.md) and [upgrade guide](https://github.com/marmot-protocol/mdk/blob/v0.11.0/docs/integration/0.11.0.md), not an assumption that every 0.9 patch is wire-identical.

**Legacy policy, precisely:** MDK v0.11.0 still contains legacy-profile *read/operate* paths for already-joined groups, but production creation of legacy groups is disabled, new invitations/KeyPackages are current-profile only, and the strict cutover freezes additions to legacy groups ([capability code](https://github.com/marmot-protocol/mdk/blob/946e0547485c9a2c393c2048ec3a968fd50fb441/crates/cgka-engine/src/capabilities.rs), [addition gate](https://github.com/marmot-protocol/mdk/blob/946e0547485c9a2c393c2048ec3a968fd50fb441/crates/cgka-engine/src/message_processor/mod.rs), [KeyPackage retirement](https://github.com/marmot-protocol/mdk/blob/946e0547485c9a2c393c2048ec3a968fd50fb441/crates/cgka-engine/src/key_package.rs)). Its retained `Legacy` profile uses an `0xf2f1` proof (v0.9.0 used v1 proof bytes); MDK **0.8** legacy groups used an `0xf2ee` monolith and lack that proof. Thus source inspection does *not* establish that 0.11 reads or writes 0.8 groups. No in-place upgrade of a group's MLS GroupContext across these profiles is specified; recreate/reinvite into a new current-profile group, preserving old history locally and labeling the handoff. Never auto-fallback on cryptographic parse/auth failure.

**Account proof:** yes, MDK current-profile leaves emit and verify the adopted 104-byte `0x8009` proof (32-byte account id, 8-byte timestamp, 64-byte BIP-340 signature); it is produced via an unpublished kind-450 signing template. Old deployed MDK legacy leaves carry `0xf2f1`; v0.8 leaves have no compatible proof. See [MDK proof construction/validation](https://github.com/marmot-protocol/mdk/blob/946e0547485c9a2c393c2048ec3a968fd50fb441/crates/cgka-engine/src/account_identity_proof.rs) and [spec bytes](https://github.com/marmot-protocol/marmot/blob/07da8ffbfa7aa6c1e73e8e326085d0c47dc298e7/app-components/account-identity-proof-v2.md).

## Ordered implementation and release gates

1. **Freeze pins and executable differential fixtures.** Keep MDK 0.8 W23 unchanged; add a second container/driver built from immutable MDK v0.11.0 source and `Cargo.lock`, plus v0.9.0 as an explicit **expected-incompatible** historical probe where its API can run. Do not weaken v2-proof validation to make 0.9.0 green. The driver must report engine SHA/profile and classify `unsupported` separately from crypto failure.

## Contents

- `engine_default`: two MDK `cgka-engine` instances (`Engine` with
  `ProtocolProfile::Current`, the default feature registry, supported
  components = cgka-engine defaults `0x8001 0x8003 0x800c` plus Nostr routing
  `0x8004`, and the real `NostrMlsPeeler`). The joiner makes a KeyPackage
  (`fresh_key_package`); its kind:30443 event is built with MDK's
  `NostrKeyPackagePublication` exactly as marmot-app fills it; the creator
  creates a group with a routing component (two relays) and the joiner's
  KeyPackage. Recorded: the KeyPackage (MLSMessage), its event, the joiner's
  private init/encryption keys and Ed25519 seed (read from MDK's storage
  before the join consumes them), the NIP-59-unwrapped kind:444 rumor (MDK's
  own wrap, unwrapped with the joiner's key), the Welcome, the creator's
  GroupContext extensions and ratchet tree. **Control**: MDK's joiner joined
  that Welcome (`mdk_control_join_profile` = `Current`, 2 members).
- `white_noise_app`: the same with marmot-app's feature registry
  (`app_feature_registry()`: SelfRemove required; agent-text-stream roles)
  and its group-creation components (routing, agent text stream
  `user_to_agent_default`, encrypted media v2): what every White Noise group
  requires. libmarmot refused it (`MARMOT_ERR_UNSUPPORTED`) until
  nostrc-qp24.5.2; it now joins it (`test_white_noise_welcome_joined`).
  MDK's control join succeeded.
- `openmls_negatives`: groups built directly with MDK's pinned OpenMLS (the
  engine refuses to build them) for one joiner (KeyPackage and private keys
  recorded): `Control` (valid), `BadProof` (creator proof signature bit
  flipped), `MissingProof` (creator leaf without its `0x8009` entry),
  `MixedGroup` (`0xf2ee` GroupContext extension beside the adopted state),
  `MissingRequiredCapability` (`app_data_update` not required),
  `NonAdminInviter` (admin policy names only the joiner); and `commits`
  (recaptured 2026-09-30 for W24 review L2): a valid adopted OpenMLS group
  joined by that joiner and three PublicMessage Commits from the joined
  epoch adding a third member -- valid, without its `0x8009` proof, and not
  advertising the required `0x800c` -- for the MLS-layer Commit processor's
  profile check.

The kind:444 rumors are dated at capture: the tests set
`MarmotConfig.max_event_age_secs` = 0 so they do not expire.

**Secrets.** Every secret here is test-only. Account keys are derived from
public seeds as MDK's own test support derives them
(`cgka-engine/tests/support/mod.rs`); MLS keys are random at capture. Never
use them anywhere else.

## Regenerating

```sh
git clone --depth 1 --branch v0.11.0 https://github.com/marmot-protocol/mdk.git /tmp/mdk-v0.11.0
mkdir -p /tmp/mdk-v0.11.0/crates/w24e-vectors
cp -r emitter/* /tmp/mdk-v0.11.0/crates/w24e-vectors/
# add "crates/w24e-vectors" to [workspace] members in /tmp/mdk-v0.11.0/Cargo.toml
cd /tmp/mdk-v0.11.0 && cargo build -p w24e-vectors && git diff Cargo.lock  # only w24e-vectors
target/debug/w24e-vectors emit <this dir>/adopted-groups.json
cd <this dir> && python3 gen_adopted_fixture.py
```

MLS keys are random, so a new capture has new bytes; the tests do not
depend on particular values beyond what the capture records.

## Reverse direction: libmarmot creates, MDK joins

Not a CI test (it needs the Rust build). Run on 2026-09-30 with libmarmot
at this commit (and before, with the same result):

1. `w24e-vectors joiner /tmp/w24e/rev`: an MDK v0.11.0 engine (SQLCipher
   file storage) publishes a fresh KeyPackage event.
2. A throwaway C driver: `marmot_create_group_for_profile(ADOPTED)` invites
   it (relays given unsorted) and writes the kind:444 rumor.
3. `w24e-vectors join /tmp/w24e/rev rumor.json <creator sk>`: the rumor is
   NIP-59 gift-wrapped with nostr's `GiftWrapBuilder`, peeled by MDK's
   `NostrMlsPeeler` (tag and relay validation) and joined by
   `Engine::join_welcome` (proofs, required capabilities, admin inviter).

Result:

```json
{"admins":["ab7b392a9e4b5e122cf8a20da75da49d2f4d6090d0ca3028cf671f1e39a52852"],"epoch":1,"group_id":"b8400beb86a5aa07be9e8fcf3d0a1dc9ead9a7cf0ba0a63f0eab7850cf7ae30b","members":2,"protocol_profile":"Current","required_app_components":[32769,32771,32772,32777,32780],"result":"joined"}
```

MDK accepted the libmarmot group as a current-profile group with the
libmarmot creator as admin and the required components
`0x8001 0x8003 0x8004 0x8009 0x800c`.

## Commits (`adopted-commits.json`, nostrc-qp24.5.1.3)

Same pins as above (MDK `v0.11.0` = `946e0547`, its OpenMLS
`erskingardner/openmls@59e7d3b2`, its `Cargo.lock`: adding the crate changed
the lock only by the crate's own `[[package]]` entry, checked with
`git diff Cargo.lock`; rustc 1.97.1). Captured 2026-10-01 (Pacific) by W24b
slice H. `tests/test_adopted_commits.c` reads it.

- `mdk_engine`: five MDK v0.11.0 `cgka-engine` instances (in-memory SQLite
  storage, `ProtocolProfile::Current`, the engine's default components plus
  Nostr routing, and the default feature registry with SelfRemove
  registered **Optional**, so every leaf advertises proposal 0x000a -- a
  SelfRemove needs every member's support -- while no group requires it;
  a manual convergence clock advances past the engine's quiescence and
  SelfRemove jitter instead of sleeping). Alice creates a group with Bob,
  Carol and the observer, whose KeyPackage private keys are recorded:
  libmarmot joins as the observer. Then, as kind:445 events from MDK's own
  peeler: Alice renames (0x8001); Bob (no admin) self-updates; Alice adds
  Dave; Alice makes Bob a co-admin (0x8003); Dave's SelfRemove proposal and
  the Commit Alice's auto-committer makes of it; Alice removes Carol, then
  Bob (an admin: MDK drops his key from 0x8003 in the same Commit); Alice
  rotates the routing (a new `nostr_group_id` and relays, published at the
  old address). An application message from Alice follows every Commit (and
  one precedes them).
- `openmls_forgeries`: an adopted group made with the pinned OpenMLS
  directly (admins X and W, Y no admin, the observer O), and from the joined
  epoch Commits MDK refuses to send: non-admin AppDataUpdate/Add/Remove,
  dropping a required component or the admin policy or the lifecycle, an
  empty or non-member admin list, malformed profile/routing bytes, removing
  an admin without dropping its key (and with it: valid), Adds with a
  tampered or no account proof, a disband, a malformed 0x800b, an
  AppDataUpdate of 0x8009, of an unknown id (valid), a GroupContextExtensions
  proposal; since the slice H review (`openmls_forgeries` regenerated
  2026-10-01 with the same emitter, `mdk_engine` kept as captured): lifecycle
  transitions MDK refuses (un-requiring 0x800c, alone or with a rename; a
  redundant 0x800c=active) and the control (un-requiring 0x8001, valid);
  valid 0x800b (`EncryptedMediaPolicyV2::blossom_default`) and 0x8006
  (`user_to_agent_default`, the members' leaves advertising the receive role
  0xF2D1 as libmarmot's do) updates and 0x8006 requiring send; valid and
  malformed 0x8002, 0x8007 (a non-URL) and 0x8005 (7 bytes); a removal of
  absent state and 20 updates in one Commit (valid, as MDK accepts them); X
  removing the observer with and without a malformed 0x8002; and
  `lifecycle_less`, a second group (creator XL and the observer) that has not
  enabled lifecycle-v1, with MDK's enablement Commit (valid), the enablement
  with a rename, and a lifecycle state without the requirement; and by
  reference: X's standalone rename and its Commit, Y's (no admin) and X's
  Commit of it, W's at epoch 1, X demoting W, W's at epoch 2 and X's Commit
  of it. Every forgery is built from the same stored epoch: an OpenMLS group
  that staged and cleared a Commit keeps stale state (a later Commit's
  UpdatePath then does not decrypt), so the emitter restores the member's
  whole storage after each.
